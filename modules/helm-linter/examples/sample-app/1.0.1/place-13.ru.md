# PLACE-13 — параметр под своим приложением (scope-to-app, черновик)

## Принцип

Deploy-параметр должен сидеть только в точке, **все** приложения которой принимают его по Helm-схеме.
Проверяем каждый из 4 уровней (`cloud`/`app@cloud`/`ns`/`app@ns`). Два следствия:

- **scope-down** — параметр, который на своём уровне принимает **часть** приложений (один или подмножество, но
  не все) → опустить к каждому принимающему приложению, в его `app@ns`;
- **remove** — параметр, который на своём уровне не принимает **ни одно** приложение (включая случай, когда он
  уже на app-уровне, а сам апп его не принимает) → кандидат на удаление.

Цель: в deploy-контекст приложения попадают только параметры, которые оно реально использует.

## Две оси размещения

- **Ось композиции (внутри окружения)** — какой сущности принадлежит параметр, по Helm-схеме. **Это PLACE-13.**
- **Ось географии (между окружениями)** — на каком слое `env→cluster→repo→template` живёт значение, по
  единообразию. Это `PLACE-1` (+`PLACE-12` для template).

PLACE-13 ставит координату композиции; подъём по географии — не он.

## Стек приоритета (deploy) — 4 уровня

От широкого к узкому, правый перебивает левый:

```text
cloud  <  app@cloud  <  ns  <  app@ns
```

- `cloud` — облако целиком: все приложения всех неймспейсов облака;
- `app@cloud` — облако, одно приложение: это приложение во всех его неймспейсах облака;
- `ns` — неймспейс целиком: все приложения неймспейса;
- `app@ns` — неймспейс, одно приложение: только это приложение в этом неймспейсе (цель переноса).

## Вход

Крутим **от точек ассоциации**, не от файлового размещения. Deploy-параметры окружения берём через
effective-проекцию линтера и рассматриваем по **точке ассоциации** (`cloud` / `app@cloud` / `ns` / `app@ns`).
Точку даёт **инвенторка**: `env_definition.envTemplate.envSpecificParamsets` (ключ = `cloud` или deploy-postfix
неймспейса) + наличие секции `applications[]` в ParameterSet'е. Файл (резолвится Inventory → cluster → site) —
вторичен.

**Скоуп сейчас — только инстанс-авторённые параметры** (анализ и фиксы). Template-слой **отложен** (включим
позже). Ограничение-следствие: приоритет-чек (шаг 6) видит только инстанс-уровни; template-авторённое значение,
затеняющее на промежуточном уровне, пока может быть пропущено — ловит оракул (до включения template-скоупа).

- **Паспорт** — не здесь: `PLACE-4` забирает контрактные паспорт-ключи **раньше** (order+capture), PLACE-13
  идёт по остатку. Без порядка контрактный ключ (он может быть в схеме аппа) ошибочно уехал бы в апп.
- **Кред-макро в значении — не исключаем.** Обычный deploy-ключ; значение-макро трактуем как непрозрачный
  литерал (для сравнений в шагах 6/8).
- **Вне входа:** e2e/runtime (другие категории), Resource Profile (отдельный объект), credential-файлы.
- **НЕ читаем** сгенерированные `Cloud`/`Namespace`/`Application` объекты — они рендерятся; фикс идёт в
  авторский источник.
- **НЕ читаем** ES

## Каталог supportedParameters

Строит `generate_helm_parameter_catalog.py` (скилл `helm-schema-parameter-catalog`), один раз. PLACE-13 читает
готовый `<app>.yaml`: `supportedParameters` (union ключей), `parameters[].definedByServices`,
`services[].parameters[]` с флагами `type`/`additionalProperties`/`internal`/`envSpecific`. Сборка:
SD → AppDef/RegDef → DD → `services` → per-service `values.schema.json` → union; сервис без схемы →
`unresolvedServices`. Декомпозиция по сервисам = разбор umbrella/сабчартов.

Топологию «какой апп в каком неймспейсе» (шаг 2) берём из SD/deploy-plan по `deployPostfix` аппа (есть и в
каталоге), **не** из `supportedParameters`. Допущение (из контракта скилла): у аппа **одна версия** по всем
анализируемым окружениям — иначе сборщик каталога падает (имена version-independent), да и схемы могли бы
расходиться. Отсутствие AppDef/RegDef/DD/registry-cred → blocking-ошибка сборки (тогда у правила нет входа).

## Алгоритм

Повторять для **каждого окружения**, для **каждого его инстанс-авторённого deploy-параметра** «ключ = значение»:

1. **Определить уровень** параметра — один из `cloud` / `app@cloud` / `ns` / `app@ns`.
2. **Определить затронутые приложения** — кого этот уровень достаёт: `cloud` → все приложения облака; `ns` →
   приложения этого неймспейса; `app@cloud` / `app@ns` → только это одно приложение.
3. **Определить приложения потребителей** — из затронутых те, чей чарт принимает ключ по схеме (ключ под
   `additionalProperties`-картой считается принятым; ключ с пометкой `internal`/`envSpecific` пропускаем).
4. **Если у затронутого приложения есть хоть один `unresolved`-сервис** → его `supportedParameters`
   неполный, вердикт «принимает / не принимает» недоказуем → «на ревью», следующий параметр.
5. **Сравнить потребителей с затронутыми:**
   - потребители = **все** затронутые → параметр стоит правильно, **следующий параметр**;
   - потребителей **ноль** → «**кандидат на удаление**» (на ревью), **следующий параметр**;
   - потребитель **один** или **несколько, но не все** → для **каждого** потребителя идём в шаг 6.
6. **Приоритет-чек** (только для переноса, т.е. для источника выше `app@ns`): стоит ли **этот же ключ** на
   уровне **строго между текущим и `app@ns`** по стеку `cloud < app@cloud < ns < app@ns` — с **другим**
   значением?
   - **да** → перенос изменит эффективное значение → «**на ревью**», следующий потребитель;
   - **нет** → шаг 7.
7. **Предложить перенос:** положить «ключ = значение» в парамсет `<prefix>-<приложение>-deploy` на уровне
   `app@ns` (в каждом неймспейсе, где приложение развёрнуто) и **убрать** ключ с исходного уровня.
8. **Если файл-источник делят несколько окружений** (общий `cluster`/`site`-ParameterSet) — переносить/удалять
   можно, только если шаги 2-7 во **всех** этих окружениях дали **одного** владельца. Согласие → правка на
   общем файле (он остаётся общим). Разошлись → **разделить** по окружениям. Механика как в PLACE-12.

**Не входит:** подъём вверх — соседние правила: `app@ns → app@cloud` (значение одинаково по всем неймспейсам
приложения) и выше по окружениям/кластеру/шаблону (`PLACE-1`/`PLACE-12`).

## Почему приоритет-чек (шаг 6)

Цель переноса — `app@ns`, **верх** стека. Перенос вверх может перекрыть промежуточную установку. Пример:
`cloud: TIMEOUT=30` и `ns: TIMEOUT=10`. Сейчас приложение получает `10` (`ns` сильнее `cloud`). Перенос
`cloud`-значения `30` на `app@ns` сделает его сильнее всех → приложение получит `30`. Это регрессия → шаг 6
ловит «ключ стоит между источником и `app@ns`» → на ревью.

## Почему гейт согласия (шаг 8)

Один ParameterSet-файл может быть подключён к **нескольким окружениям** сразу — например, кластерный
`environments/<cluster>/parameters/…` используют все окружения кластера. Правка такого файла затронет все эти
окружения **разом** (файл один). А владельца ключа считаем **для каждого окружения отдельно** (у каждого свои
приложения и схемы), и он может оказаться **разным**. Нельзя одной правкой отправить один ключ и в `billing`
(для env1), и в `catalog` (для env2) — entry один.

Поэтому: согласие всех делящих окружений на **одного** владельца → перенос на общем файле (он остаётся общим);
расхождение → **разделить** по окружениям. Чисто per-env файл (`Inventory/parameters/`) принадлежит одному
окружению — согласие само собой, шаг 8 не нужен.

Пример. Общий кластерный файл с `LOG_ENDPOINT`, подключён к `env1` и `env2`:

- оба принимают только `billing` → согласие → перенести в `billing`;
- `env1` → `billing`, `env2` → `catalog` → разошлись → разделить по окружениям.

## Нейминг per-app ParameterSet

`<project-prefix>-<application>-deploy`. Линтер резолвит **только `<application>`** (вычисляется) и `-deploy`;
`<project-prefix>` — литеральный слот для читателя. Пример: `<project-prefix>-CLOUD-BSS-CPQ-deploy`. Приоритет —
влить в существующий `<…>-deploy`. Паттерн из ai-helpers `saas-envgene-adaptation`; `<subject>` из NAME-4 здесь
= имя приложения (вычислено), project-prefix — не дело линтера (снимает конфликт NAME-4 ↔ helper, task #1).

## Типы находок

У линтера есть ось `Action`: **ревью** (человек решает) и **Fix-grade** (применимо). Детерминированный перенос
(один или подмножество потребителей, схемы разрешены, шаг 6 пройден по каждому) → Fix-grade по каждому
переносу; неоднозначное (удаление, unresolved, промежуточная установка на шаге 6, расхождение по окружениям)
→ ревью.

Линтер Report-only: линтер файлы не правит, применяет фиксер + оракул (сверка ES) +
человек.

## Трассировка

**Перенос.** `BILLING_RETRY = 5` на `cloud`. Приложения облака: `billing, payments, catalog`.

- Шаг 2: затронуты все три. Шаг 3: схему принимает только `billing` → потребитель один. Шаг 5: один из трёх →
  шаг 6. Шаг 6: `BILLING_RETRY` больше нигде не задан → безопасно. Шаг 7: перенести в `<prefix>-billing-deploy`
  (`app@ns`), убрать с `cloud`. Больше не доходит до `payments`/`catalog`.

**Удаление.** `LEGACY_FLAG = true` на `app@ns` приложения `billing`.

- Шаг 2: затронут только `billing`. Шаг 3: чарт `billing` ключа не принимает → потребителей ноль. Шаг 5: ноль
  → «кандидат на удаление» (ревью + сверка ES).

## Края

- umbrella-root-only значения (которые зонтик потребляет сам, не под сервисом) каталог не ловит → возможный
  ложный «кандидат на удаление»; ловит человек/оракул;
- удаление не проходит шаг 6 (цели переноса нет) — непреднамеренный эффект на ES ловит оракул + человек;
- форма ключа сабчарта (`foo`) vs umbrella-вложенная (`<alias>.foo`) — каталог хранит сабчарт-локальную; матч
  в той же форме, в какой параметр лежит в инстансном репо;
- удаление — всегда ревью при любой неполноте схемы; молча не удаляем.
