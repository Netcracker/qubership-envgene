# SEC-5: review the protection of connected secrets

Status: implemented. The accepted SEC-5 contract below is covered by synthetic tests and independent review; supported scope and static-analysis limits remain explicit.

## Confirmed requirements

The user chose **Information / Review** for every SEC-5 finding, including a visibly unprotected value. Do not escalate these findings to Warning / Fix.

Accept these ways of supplying secrets:

- SOPS-encrypted values.
- References to secrets supplied by GitLab or GitHub CI/CD.
- Automatic CI/CD lookup explicitly supported by EnvGene, even when no YAML reference exists.
- External Credentials (`type: external`) matching the local schema. `secretStore` is optional and defaults to `default_store`; stored `data`, unsupported keys or malformed properties are not accepted.

When the source of a secret cannot be determined statically, report Information / Review. Do not describe an unknown expression as a confirmed plaintext secret.

Inspect connected entities only. Never include secret values in findings, run decryption, inspect the agent's environment for secrets, or contact CI/CD and secret-store services.

The original SEC-5 is an optional repository-wide SOPS recommendation. This project interprets it as a review of secret protection with the alternatives agreed above. It does not require `crypt: true` or SOPS when secrets come from an accepted external source.

## Expanded scope

The approved scope expands connection resolution to system Credentials, selected Cloud Passport and deployer companions, and generated environment Credentials. The implementation plan keeps these as distinct security-source records alongside the existing connection model.

Retain the existing selected shared Credential inputs and `Inventory/credentials/inventory_generation_creds.yml`. A selected whole-file generator input is inspected as a whole; entries selected only through an individual system reference are inspected only when referenced. Preserve this distinction in the connection data.

Inspect selected ParameterSets (`parameters` and `applications[].parameters`), all three parameter sections in selected Cloud/Namespace objects, and secret-bearing fields in selected passports and system/deployer configuration. Use SEC-1's name heuristic for parameter bags; use documented credential fields in system configuration. Recognized Credential references participate regardless of parameter name.

### Additional connection resolution

| Source | Evidence of use and selection |
| --- | --- |
| Generated environment Credentials | For each discovered environment, select its existing `Credentials/credentials.yml`, the fixed input read by EnvGene's `Environment` object. Do not recursively scan similarly named files in arbitrary directories. |
| Cloud Passport companion | Start from a uniquely resolved, selected passport. In its directory, try `credentials/<passport-stem>.yml` first, then `<passport-stem>-creds.yml`. Select only the first existing candidate. This follows the local `add_cloud_passport_creds` implementation. |
| App/cloud deployer | Require `inventory.deployer` in the environment definition. Search cluster level before environment level; at each level try `app-deployer` before `cloud-deployer`, and basename `deployer` before `app-deployer`. Match `.yml`/`.yaml` through the local helper's encounter order. The first definition file is selected; if the requested deployer entry is absent, fall back to `configuration/deployer.yml`. Inspect only the selected entry, not every deployer listed in the file. |
| Deployer companion | Resolve Credential references from the selected deployer entry against `deployer-creds.yml` beside the definition, then `credentials/credentials.yml` beside it. Inspect referenced entries; an inline token is checked at its consumer position without requiring a companion. |
| System Credentials | Follow recognized references from active system configuration fields to `configuration/credentials/credentials.yml`. The known repository integration configuration is a system input; registry definitions require a resolved registry consumer, and deployers require the binding above. Do not mark all root Credential entries used merely because the file exists. |

For system and deployer fields, support the documented `envgen.creds.get('id').field` syntax; runtime parameter maps use `${creds.get('id').field}`. Local calls must select `username`, `password` or `secret`, and a syntax used in the wrong context is unknown even when its target is protected. Recognize bare `credentialsId` only in a documented Credential-reference field with an established consumer; it selects the whole entry, while an arbitrary string key is not a reference. Expressions stored inside Credential `data` are unknown rather than recursively evaluated because the generator returns stored data verbatim.

An absent integration `self_token` uses the documented `GITHUB_TOKEN` / `GITLAB_TOKEN` fallback and produces no SEC-5 finding. An explicit value takes precedence and must be inspected; do not excuse an inline token because a CI/CD variable could exist. The scanner does not check whether CI/CD actually contains that variable.

A recognized reference whose catalog or Credential entry is unavailable produces no finding at the consumer: no secret content is available to inspect. Unsupported registry associations or syntax still produce unknown-source Review. Do not guess a target or scan all potential targets. Version-dependent forms not supported by the inspected local generator are unknown, not additional implicit search paths.

Require paths inside the repository and outside `.git`, including symlink targets. An unsafe or unreadable first-priority candidate must not cause a silent fallback to a lower-priority file. Deduplicate physical inputs while retaining environment, source kind, selected entries and consumer locations. Guard against cyclic YAML aliases and reference cycles.

### Architecture and boundaries

Add explicit security-source records and per-environment links alongside existing connection sets. Keep source kinds separate: a passport companion is not a shared Credential merely because both contain Credential entries. SEC-5 consumes the expanded records; existing rules retain their established selection until their own contracts explicitly use a new source kind. Add regression tests proving the expansion does not silently change their findings.

Resolve references within the correct source context. System and deployer references use their selected companion catalogs; runtime parameter references use the environment's generated Credentials when present. Shared/passport source inputs are independently inspected as generator inputs. If a generated catalog is unavailable, do not guess merge precedence across input files: unavailable reference targets are skipped. Do not merge unrelated same-ID definitions across environments.

Effective Set outputs are not included in this expansion: their flat secret maps and artifact-consumption links require a separate contract. Neither are arbitrary CI workflow files, inactive registries, unused deployer definitions, unrelated passport companions or historical copies. The rule reports its supported scope rather than claiming universal secret detection.

## Classification

| Observed state | SEC-5 result |
| --- | --- |
| SOPS metadata with a nonblank version, encrypted MAC and supported recipient identity plus encrypted key data, and a structurally recognizable SOPS token for the inspected value | No finding for that value; no claim of cryptographic verification |
| SOPS metadata but a plaintext secret value in the same document | Review the plaintext candidate; metadata does not exempt a whole file |
| SOPS-looking value without usable metadata, or malformed encryption marker | Review: protection cannot be established |
| Recognized external Credential reference | No plaintext-secret finding for the reference; do not access the remote store |
| Recognized reference resolving to a selected local Credential | Inspect the target value; the reference alone does not establish protection |
| Missing, ambiguous or unsupported reference target | Review: source cannot be established |
| Expression or template with an unknown source | Review: source cannot be established |
| Literal secret candidate without encryption | Review: a literal secret candidate needs protection |
| Fernet marker | Review: this encryption format is outside the agreed accepted formats; do not call it plaintext |
| Absent, null or empty value | No SEC-5 secret-material finding |

In local Credential entries, inspect nonempty leaves under `data`. Do not classify IDs, `type`, SOPS metadata or external-store addresses as secret values. For parameter bags, retain SEC-1's name-based detection limits: this is not general secret discovery.

A `${NAME}` expression alone does not establish that a value originates in CI/CD. Accept a CI/CD reference only when its evaluation context is explicitly supported by the local EnvGene implementation; otherwise use the agreed unknown-source Review. Never verify variable existence by querying CI/CD or by reading local process variables. Do not invent a new substitution syntax.

Treat complete recognized expressions separately from strings that combine expressions with literal fragments: do not mark an entire composite string protected merely because part of it is a reference or encrypted token. Unsupported composition needs Review.

A selected unreadable, Jinja or structurally unsupported input receives one generic file-level Review explaining that protection could not be inspected. This includes a present, nonempty parameter section with the wrong container shape. Do not print parser exception text. Missing unselected files do not become scan targets.

`crypt` and `crypt_backend` do not establish protection of stored values. This rule does not require changing either flag and does not change existing SEC-1, SEC-3 or SEC-4 behavior. Overlap with those rules is possible; their placement/runtime/shape checks answer different questions.

## Reporting

Emit findings at the affected value, incompatible reference or unreadable file. Prefer one finding per definition/value over repeating the same local-secret finding at each consumer. Do not emit findings merely because a recognized reference target is unavailable. Deduplicate repeated use across environments and aliases, preserving a relevant location.

Use generic messages that distinguish unprotected candidates, unsupported encryption and unknown sources. Include file, line and column, but no values, Credential IDs, variable names, expression text, remote-store paths or parser excerpts in message, hint, key or related text. Use a generic key such as `secret` rather than a Credential-ID-bearing YAML path. File paths remain visible for navigation.

Integrate SEC-5 after SEC-4 in the catalog, engine and console order. Preserve CLI exit behavior and existing HTML conventions.

## Verification and delivery

Use synthetic fixtures for each classification row, connected versus unused inputs, nested and application parameters, cyclic aliases, safe paths, repeated references, ambiguous definitions, partially encrypted files, encrypted `type` fields, valid external entries and unsupported external shapes. Check that unknown sources produce Review rather than being silently skipped. Assert non-disclosure in findings, console and HTML.

Deliver the rule, meaningful tests, English/Russian specifications and seven-section algorithm documents, and updated usage/catalog documentation. Run the relevant tests and then the full suite. Local corpus inspection may report aggregate findings only and must not modify the corpus or contact the network. Include source-selection regressions for passport/deployer priority, shadowed files, system entry-level selection, CI/CD fallback versus explicit overrides, generated catalogs, reference cycles and unchanged existing-rule outputs.
