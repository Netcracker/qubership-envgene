# SEC-3: Credential references in runtime parameters

Status: implemented; this specification retrospectively records the agreed scope and current recognition limits.

## Requirement and interpretation

Credentials must not enter `technicalConfigurationParameters`, whose runtime values are exposed through Consul. The agreed scope includes ParameterSets connected as technical parameters. Move secret use to deployment parameters while retaining a Credential reference.

This implementation detects Credential references. It does not detect every possible secret: literal values with secret-like names are covered separately by SEC-1.

## Scope

Inspect selected ParameterSets only when at least one resolved use has the technical category (`envSpecificTechnicalParamsets`). Check `parameters` and `applications[].parameters`. A file used for both technical and other categories still participates; deployment-only and E2E-only files do not. A missing technical reference does not select another file.

For object files, use the shared selection: `cloud.yml` of discovered environments and Namespace files selected by resolved ParameterSet uses or resource-profile bindings. Inspect only `technicalConfigurationParameters` in these objects.

Require existing paths inside the repository and outside `.git`, including symbolic-link targets. Skip unreadable or malformed object documents and unloaded or Jinja ParameterSets. Traverse nested mappings and lists with cycle protection; avoid repeated inspection of the same physical object file.

## Detection contract

- A mapping with `$type: credRef` is one reference occurrence. Do not report its individual fields separately.
- A string matches when it contains the direct expression-call prefix `${creds.get(`, allowing whitespace between syntax elements. Composite strings also participate. Recognition does not require validating the full expression, Credential identifier or target field.
- Plain `creds.get(...)` text outside an expression and unrelated macros do not match. A quoted occurrence inside a different expression, such as `${"creds.get(...)"}`, does not match this prefix.
- Report each matching parameter once even if its string contains several calls. Parameter names do not affect detection; any Credential field participates.

## Findings and boundaries

Emit **Warning / Fix** at the parameter's YAML position with its full key and scope. Explain that a runtime parameter contains a Credential reference and suggest moving secret use to deployment parameters. Do not include the reference text, Credential identifier, value or parser exception text. Sort by path, key and line.

No indirect-expression analysis, Jinja rendering, Credential existence checks, external-store access or automatic changes are introduced. Skipped expressions are not proven safe. Preserve CLI exit behavior; findings from other rules remain independent.

## Verification

Synthetic fixtures must cover both reference forms, whitespace, composite strings, nested mappings and lists, application parameters, all Credential fields, repeated calls, technical and mixed-category selection, deployment/E2E exclusions, Cloud and Namespace scope, unused and missing inputs, cyclic aliases and safe paths. Check positions, report integration and non-disclosure of tested values and identifiers.
