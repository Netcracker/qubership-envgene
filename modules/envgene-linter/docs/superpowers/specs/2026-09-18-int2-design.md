# INT-2: every reference resolves

Status: implemented and verified. The full suite passed 613 tests, including 41 INT-2 tests; independent final code review found no blockers. Corpus verification is recorded separately.

## Confirmed requirements

Inspect supported references in connected entities only. A definitely missing or ambiguous target is **Warning / Fix**; a dynamic reference, unreadable source or unavailable template context is **Information / Review**. Do not infer a broken reference from missing generation inputs alone.

Support Credential calls with and without property access, calls embedded in larger strings, structured `credRef`, known bare `credentialsId` fields, ParameterSet references and Resource Profile references. Credential validation ends at object existence: do not validate type, required properties, selected property availability or secret completeness.

Do not expose IDs, expressions, parameter names, secret values or parser excerpts in findings. Preserve navigable file, line and column locations. Do not fetch external templates, render Jinja, execute macros, decrypt values, access secret stores or inspect process secrets.

## Connected consumer scope

Reuse the established connection graph and security-source selection without widening older rules' legacy connection sets. Inspect connected ParameterSet parameter maps, application parameter maps and selected Cloud/Namespace parameter sections. Follow recognized references from selected system/deployer fields, active registry consumers and selected Artifact Definitions. A directory's existence does not make every object in it a consumer.

Runtime parameter calls use `${creds.get('id')}` with optional property access; system/deployer calls use `envgen.creds.get('id')`. Both may occur within a larger string. A structured mapping uses `$type: credRef` and `credId`. Bare IDs count only in documented consumer fields such as `credentialsId`, `defaultCredentialsId` and `tokenSecret`. Dynamic IDs and incomplete/unsupported recognizable call syntax are unknown. Arbitrary strings are not assumed to be references. Do not recursively interpret expressions inside Credential `data`.

For INT-2, an explicit ParameterSet or Resource Profile binding target also selects an existing `Namespaces/<target>/namespace.yml`, even when its bound ParameterSet or template is unavailable. Inspect its parameter sections, `credentialsId`, ParameterSet lists and profile fields. This does not widen other rules' scope.

For `profile.name`, `profile.baseline` and `profile.override_name`, first search `<environment>/Profiles`; multiple physical targets are ambiguous. With no generated target, a baseline remains unknown, while name/override use local lookup with possible unavailable template context. An unsafe or unavailable higher-priority directory blocks fallback and yields unknown; logical directory inspection does not follow external symlinks.

## Resolution contract

### Credentials

Use the selected system/deployer catalog for those consumers. Runtime references use the environment's generated `Credentials/credentials.yml` when present. That catalog is authoritative, including an empty catalog: a missing ID is a definite missing target. A selected catalog that is unreadable, unsafe or structurally unsupported makes the result unknown and must not cause fallback to unrelated inputs. The metadata key `sops` is not a Credential object.

When the generated runtime catalog is absent, a defined mapping entry in connected shared Credentials or the selected Cloud Passport companion can establish existence. Apply the passport companion first, then shared inputs in list order; the last definition of an ID determines its final entry. Repeated IDs across list-ordered shared inputs are not automatically ambiguous. Multiple physical files in one selected lookup bucket may be ambiguous; aliases of one physical file are one target. An ID absent from authored inputs remains unknown because template generation and macros can provide IDs. Never search another environment or unused Credential files to satisfy a reference.

### ParameterSets

Inspect deploy, E2E and technical `envSpecificParamsets`, `envSpecificE2EParamsets` and `envSpecificTechnicalParamsets` bindings plus `deployParameterSets`, `e2eParameterSets` and `technicalConfigurationParameterSets` in selected Cloud/Namespace objects. During ParameterSet staging, a cluster file replaces the same site filename; Inventory fragments then join the staged files for deterministic merging. Multiple matching fragments, including separate supported extensions, do not imply ambiguity.

A missing local binding is unknown when `envTemplate.name`, `artifact` or `templateArtifact` supplies a possible template source. Without a template source, a closed local binding with no target is definitely missing. Missing references from rendered Cloud/Namespace objects remain unknown when an unavailable template can supply them. Unreadable/Jinja targets cannot establish resolution.

### Resource Profiles

For `envSpecificResourceProfiles`, search environment `Inventory`, then cluster, then `environments`. At each level search `resource_profiles`, `rp_override`, `Profiles`, then `parameters`. Stop at the first matching directory. Multiple distinct physical matches within that directory are ambiguous; shadowed lower-priority matches do not create ambiguity.

Inspect selected Cloud/Namespace `profile.name`, `profile.baseline` and `profile.override_name`, with applicable generated `Profiles` lookup. Preserve the distinction between instance override lookup and template/generated profiles. An unavailable template profile or baseline is unknown rather than a definite missing local override.

## Reporting and boundaries

| State | Result |
| --- | --- |
| Object exists in the applicable source context | No finding |
| Target definitely missing | Warning / Fix |
| Selected lookup is ambiguous | Warning / Fix |
| Dynamic, unreadable or unavailable context | Information / Review |

Report at the consumer location with a generic kind such as `Credential`, `ParameterSet` or `Resource Profile`. Deduplicate repeated physical findings while retaining environment and outcome. Sort deterministically. Keep parser text and referenced IDs out of messages, hints and keys. File paths remain visible; no change to other rules' output contract is implied.

All file access must stay inside the repository and outside `.git`, including symlink targets. Protect recursive traversal against cyclic aliases. An unreadable consumer cannot supply individual reference positions; shared discovery may report a skip instead. Unsupported consumer shapes are not full schema validation and must not be advertised as such.

Integrate INT-2 after SEC-5 and before NAME-1. The console has eighteen headings, including empty rules; HTML preserves sections only for rules with findings. Findings keep CLI exit code `0`. No flags or automatic fixes are added. SEC-5's separate secret-protection behavior remains unchanged.

## Verification and delivery

Deliver the rule, synthetic tests, English/Russian specifications and seven-section algorithm documents, README coverage and catalog integration. Verify resolved/missing/dynamic Credential forms, generated catalog authority, shared/passport fallback, environment isolation, ordered overrides, unreadable targets, ParameterSet merging and template uncertainty, Resource Profile precedence/ambiguity and generated targets, unused inputs, safe paths, cyclic aliases and report redaction. Verify engine, console and HTML integration and existing behavior with the full suite. Record actual results only after running checks. Local corpus inspection must be read-only, avoid networking and report aggregates without sensitive values.

Final local corpus verification: 25 instance repositories completed without exceptions in 91.2 seconds. INT-2 produced 1,202 Warning / Fix findings and 4,186 Information / Review findings. These are static-check results, not manually confirmed generation failures. Only aggregate counts were output; repository files were not modified and no network access occurred.
