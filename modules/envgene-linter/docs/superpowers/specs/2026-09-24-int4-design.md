## Intent and accepted decision

Implement [INT-4 in the configuration standard](/docs/configuration-standard.md#int-4---no-unreferenced-entities-should)
to help maintainers review authored entities for which the linter finds no references.
The user approved Information / Review findings for uncertain candidates, with an explicit reason for uncertainty.
The linter must say that no references were found in available sources. It must not claim that removal is safe.
Automatic deletion is outside the scope of this rule.

The user approved this specification on September 24, 2026.
It covers ParameterSet files, Shared Template Variable files, Resource Profile Override files, and individual
Credential entries identified internally by their IDs. Individual parameters and template variable keys belong
to other rules, including INT-5.

## Scope and limitations

The first version analyzes the local instance repository without fetching template repositories, rendering Jinja,
decrypting credentials, or adding runtime dependencies. Local sources cannot establish that all external consumers
are absent. Therefore, all candidates with no observed reference produce Information / Review findings in this version.
There is no Warning / Fix mode for supposedly confirmed unused entities.

Referenced entities produce no INT-4 finding. An unresolved or dynamic reference leaves affected candidates uncertain.
Its presence does not prove that every candidate is used and does not suppress the review findings.
The reason must make that uncertainty visible.

INT-4 needs an explicit exception to the
[connected-only scope](/modules/envgene-linter/docs/superpowers/specs/2026-09-11-connected-only-design.md):
its candidate catalog includes unconnected authored entities. This exception does not broaden inputs to other rules.
Generated objects can provide evidence of a reference, but they are not cleanup candidates.
The first version does not inventory entities inside template repositories.

## Candidate selection

A candidate is a recognized authored file, or an individual Credential entry, whose references will be examined.
Discover candidates at repository, cluster, and environment Inventory scopes, including scopes without consumers.
Use the existing discovery exclusions for directories that are not clusters or environments.

- ParameterSets: use the indexed YAML files under each scope's `parameters` directory, before staging or merging.
  Preserve nonrecursive ParameterSet discovery.
- Resource Profile Overrides: recursively inspect `resource_profiles`, `rp_override`, and authored Inventory `Profiles`.
  A file under `parameters` is also a profile candidate only when an explicit profile binding identifies it.
  Do not classify every ParameterSet as a profile because the resolver supports that legacy directory.
- Shared Template Variables: recursively inspect `shared-template-variables` and `shared_template_variables` at
  the three scopes. Also include files positively identified by existing bindings in legacy `configuration`,
  `configurations`, and Inventory fallback locations. Arbitrary YAML in those legacy locations is not a candidate.
- Credentials: inspect individual mapping entries in authored shared Credential catalogs under `credentials`,
  `Credentials`, and `shared-credentials` at the three scopes. Include the root system catalog and companion
  catalogs identified by the existing passport and deployer source-selection rules.

Support `.yml` and `.yaml`. Do not analyze `.j2` candidate contents or report entries invented from unreadable YAML.
Empty, malformed, or structurally invalid candidates produce a generic skip note rather than an unused-entity finding.
An empty valid Credential catalog has no entries to report.
Unselected companion catalogs outside recognized typed directories are outside the first version's candidate coverage.

Exclude generated environment `Credentials/credentials.yml`, generated environment `Profiles`, and generated
Cloud/Namespace objects from candidates. Distinguish these paths from authored files under Inventory.
Fixed inventory-generation credentials have an implicit consumer and are not cleanup candidates in this version.

Keep logical paths for scope and navigation, and deduplicate physical files.
Credential identity consists of its physical catalog path and entry ID. Equal IDs in different files are not
automatically the same candidate. Read only paths inside the repository and outside `.git`, without following
directory symlinks. Unsafe, broken, or cyclic file aliases provide no candidate or positive reference evidence.

## Reference analysis

Count direct references in recognized typed sources. Do not perform transitive dead-code elimination:
a reference inside an unconnected authored ParameterSet can protect its Credential target when its lookup context
is known. Comments, arbitrary strings, and equal values are not references.

Collect references from these local sources:

1. Raw environment definitions: all supported `envSpecific*` bindings, `sharedTemplateVariables`, and
   `sharedMasterCredentialFiles` selections. Inspect raw values so dynamic or invalid entries are not silently lost.
2. Authored ParameterSet parameter bags and generated Cloud/Namespace parameter bags: `creds.get` expressions
   and structured `credRef` references.
3. Generated Cloud/Namespace objects: top-level `deployParameterSets`, `e2eParameterSets`, and
   `technicalConfigurationParameterSets` lists, supported profile selectors, and known bare Credential ID fields,
   including namespace credentials, default credentials, and service connection credentials.
   Inspect local namespaces even when no explicit ParameterSet binding selects them.
4. Selected Cloud Passports, deployer definitions, registry definitions, integration configuration, and artifact
   definitions: the supported Credential fields and catalogs already described by INT-2 and security source selection.
   Do not recursively interpret secret values inside Credential catalogs as reference expressions.

Follow existing lookup semantics for each reference type. Associate every reference with its environment, category,
target, and catalog when those are known. A reference in one environment cannot protect an unrelated environment's
candidate. A repository or cluster candidate used by any applicable environment is referenced.
References in scope-wide authored sources apply to environments that can consume that source.
If none exist, retain the reference as unresolved context and explain the gap on affected candidates.

A literal file reference protects matching definitions in its applicable lookup scopes, including definitions
shadowed by another scope. INT-3 owns cross-scope naming conflicts. Losing first-match resolution alone must not
cause an INT-4 finding. Do not extend this protection to sibling environments or unrelated clusters.
Canonical Shared Template Variable candidates outside the current resolver's search locations remain reviewable
unless applicable positive reference evidence exists. Their finding explains the lookup limitation.

A shared Credential filename binding establishes a catalog context, not use of every entry in that catalog.
Only a supported entry reference protects an entry. Parse every literal credential call in an expression and handle
structured references separately. Reuse INT-2's distinction between literal references and unresolved expressions.
Known implicit consumers take precedence over absence of an explicit call.

When a generated Credential catalog supplies an ID, protect matching entries in its applicable connected authored
catalogs conservatively. Do not infer exact origin by comparing secret values. Equal IDs in unrelated or unconnected
catalogs are insufficient. For system, passport, and deployer references with an explicit catalog, use that catalog.
A template profile baseline name alone does not select an instance Resource Profile Override with the same stem.

Record analysis gaps by source, entity type, and applicable scope. Reasons include dynamic references, unavailable
template or rendering context, unreadable consumers, missing catalog provenance, and no discovered consuming environment.
An unreadable candidate is skipped, while an unreadable consumer adds uncertainty to the candidates it could consume.
If its scope cannot be determined, widen uncertainty conservatively rather than claiming complete coverage.
Positive evidence still protects a candidate even when other sources are unavailable.

## Findings

Emit one finding per unreferenced physical file and entity type, or per unreferenced Credential entry.
Aggregate applicable uncertainty reasons across consuming environments into that finding.
Use deterministic ordering by logical path, entity type, and source position.

Use Information severity and Review action through the existing finding model.
For file candidates, locate the finding at line 1, column 1.
For Credential entries, locate the entry key and use a generic finding key, without copying its ID into messages.
Use an existing scope label and the candidate's navigable path. Do not list unrelated candidate catalogs as locations.

Message template:

```text
No references to this {entity type} were found in the available sources.
```

The hint always states the local coverage boundary:

```text
External template consumers and rendered references are not fully analyzed. Review usage before changing this entity.
```

Append applicable specific reasons using fixed text, such as:

```text
A dynamic reference could not be resolved in this scope.
A relevant local consumer could not be read.
No consuming environment was discovered for this scope.
The generated catalog does not establish the authored entry's origin.
This location is outside the supported reference lookup paths.
```

Never include Credential IDs, secret values, source expressions, or raw parser exceptions in finding text or skip notes.
Navigable file paths remain visible. Preserve existing console and HTML report behavior and the nonfatal findings exit code.
Enable INT-4 by default after INT-3. Disabling it must bypass its additional candidate and reference analysis.

## Implementation design

Three approaches were considered: subtract selected paths from discovered files, extend the shared Connections object,
or keep an isolated usage analysis. Selected-path subtraction misses entry-level Credential use and external consumers.
Expanding Connections would expose unconnected candidates to unrelated rules. Use isolated analysis instead.

Add a dedicated usage-analysis module with typed records for candidates, observed references, and scoped analysis gaps.
It consumes `RepoIndex` and existing connection/source-selection information, then returns candidates with their
positive evidence and gaps. It must not mutate shared connections or treat `index.skipped` strings as completeness proof.
Reuse existing safe loading, path conventions, and public source-selection helpers where their contracts fit.
Do not call private INT-2 checker methods or refactor INT-2 as a prerequisite.

Add `rules/int4.py` to turn the analysis result into findings.
Register the rule in the engine, metadata, default configuration, and report ordering.
Add an algorithm reference and update scope documentation, the module readme, and the specification index.
Keep the generator and other rules' observable behavior unchanged.

## Acceptance tests

Use temporary repositories to verify observable findings, locations, and report text. Include these cases:

- Each of the four candidate types has an unreferenced and a referenced case at every supported scope.
- Two Credential entries in one selected file produce a finding only for the entry with no observed use.
- Literal calls, multiple calls in one expression, structured references, and known bare ID fields protect entries.
- Deployer, registry, integration, artifact registry, and passport consumers protect their applicable entries.
- A filename binding alone does not mark all Credential entries used.
- Same-name shadowed files stay out of INT-4 when an applicable literal reference exists.
- Equal names or IDs in unrelated environments do not suppress findings.
- A repository candidate used by one environment produces no finding even if unused by another.
- An unconnected authored ParameterSet can supply direct reference evidence in a known context.
- Generated Cloud/Namespace sources contribute references but never become cleanup candidates.
- A generated catalog protects applicable authored entries conservatively without secret-value comparisons.
- A template baseline does not protect an unrelated instance profile override.
- Dynamic references, missing templates, unreadable consumers, and absent environments produce explicit review reasons.
- Malformed candidates, Jinja candidates, arbitrary legacy YAML, and empty catalogs create no invented entities.
- Fixed inventory-generation credentials are excluded, and unrelated same-name entries remain reviewable.
- Aliases deduplicate candidates, and unsafe paths are neither read nor reported as confirmed entities.
- Findings contain no secret values, Credential IDs, expressions, or parser exception contents.
- Rule disablement bypasses analysis. Console and HTML show Information / Review, and findings retain exit code 0.

Add `testdata/rules/int4/ok` and `not-ok` examples that demonstrate positive reference evidence and review candidates.
Run regression checks for INT-2, INT-3, connections, effective merging, security rules, and report integration.
The implementation plan must distinguish existing platform failures from new failures and record actual test results.
