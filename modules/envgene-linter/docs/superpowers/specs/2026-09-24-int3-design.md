## Intent and accepted decision

Implement [INT-3 in the configuration standard](/docs/configuration-standard.md#int-3---no-shadowed-same-name-overrides-should)
as a check for one referenced filename stem defined at multiple scopes.
The scopes are the environment's Inventory, its cluster, and the repository's `environments` directory.
The rule covers ParameterSets, shared Credential files, Shared Template Variables, and Resource Profile Overrides.

The user approved checking the standard's naming requirement even when ParameterSet fragments actually merge.
The rule reports the conflicting definitions without claiming that every lower-scope file is ignored.
It does not change generation, ParameterSet merging, or the eligibility of inputs for other rules.

The standard describes first-match lookup for all four types. ParameterSet staging differs:

- A cluster ParameterSet replaces a repository ParameterSet with the same staged filename.
- An environment ParameterSet remains in `from_instance` and joins the surviving files for merging.
- Different supported extensions can survive together despite equal stems.

These behaviors are visible in
[generator staging](/scripts/build_env/main.py),
[generator processing](/scripts/build_env/build_env.py), and
[the linter's effective computation](/modules/envgene-linter/src/envgene_linter/effective.py).
INT-3 checks cross-scope naming independently of whether contents merge or replace each other.

## Requirements

- Require Python 3.12 or newer. Add no runtime dependencies.
- Run locally without rendering templates, decrypting credentials, or making network calls.
- Preserve the behavior and findings of existing rules.
- Enable INT-3 by default after INT-2 and before NAME-1.
- Emit Warning / Fix for confirmed definitions at two or more scopes.
- Keep CLI findings nonfatal, with exit code 0 and the existing report behavior.
- Never include document values, Credential IDs, or source expressions in INT-3 finding text.
- Keep file access inside the repository and outside `.git`. Do not traverse directory symlinks.

A used reference establishes the scope of analysis. Files that an existing resolver shadows can appear
in INT-3 findings because the conflict itself concerns those files. This is an INT-3 exception to
the general connected-only rule, not permission to inspect every unreferenced definition.

Credential names mean filenames referenced by `envTemplate.sharedMasterCredentialFiles`.
Repeated Credential IDs within differently named files are outside INT-3.
Generated `Credentials/credentials.yml`, root catalogs, passport companions, and fixed inventory-generation
credentials do not establish a cross-scope filename reference for this rule.

## Candidate selection

Read bindings from each discovered `EnvModel`:

- ParameterSets: deploy, end-to-end, and technical `envSpecific*` bindings.
- Resource Profile Overrides: `envSpecificResourceProfiles`.
- Shared Credential files: `sharedMasterCredentialFiles`.
- Shared Template Variables: `sharedTemplateVariables`.

Require a nonempty literal reference. Exclude `${...}`, Jinja markers, line breaks, and path expressions.
Compare the reference with the filename stem, not an internal `name` or a Credential ID.
Support `.yml` and `.yaml`. Skip `.j2` files, consistent with connected-input selection.
References from generated Cloud/Namespace objects alone do not extend this rule's input set.

Start only when the existing resolver connects a file of that type and name to this environment.
Then enumerate additional candidates along that environment's own lookup scopes.
Do not use the global selected-path union as evidence that a file belongs to another environment's reference.

For ParameterSets, use the indexed environment, cluster, and repository ParameterSets before staging removes files.
Match by stem and keep all supported extensions. Preserve the existing nonrecursive discovery contract.

For Resource Profile Overrides, use `resource_profiles`, `rp_override`, `Profiles`, and `parameters` in that order.
For shared Credential files, use `credentials`, `Credentials`, and `shared-credentials` in that order.
At each scope, retain the first directory with matches, including its supported nested files.
Continue to lower scopes to discover definitions hidden by ordinary first-match resolution.
Multiple matches confined to one scope do not trigger INT-3. INT-2 owns applicable ambiguity diagnostics.

For Shared Template Variables, follow the existing search locations: `configuration` and `configurations`
at each scope, plus the final recursive environment Inventory fallback.
Preserve this fallback's actual lookup priority when identifying the selected file.
Assign candidate scope by its logical location, not its position in the search sequence.
The Inventory fallback cannot count a file already found under its `configuration` directory twice.
Repository and cluster `shared-template-variables` directories alone are not supported lookup locations.

Deduplicate physical paths while retaining a matching logical path for location and scope.
Aliases of one physical file do not constitute two definitions, even across scopes.
When an alias belongs to a selected physical file, prefer its selected logical scope.
Sort candidates by environment, cluster, and repository scope, then logical path.

An empty or malformed YAML file still defines a filename and can participate in a conflict.
Do not parse candidate contents merely to compare names. An unreadable directory supplies no confirmed candidates.
Report a generic skip note for a failed INT-3 enumeration without including exception contents or YAML values.
Missing targets, dynamic references, and inaccessible candidates alone do not produce INT-3 findings.

INT-3 path guards apply after discovery. Existing discovery can fail on cyclic symlinks before any rule runs.
Tests for changed or cyclic candidate paths exercise INT-3 with an index prepared before the path change.
This rule does not extend the whole pipeline's error-handling guarantees.

## Findings

Emit one finding per environment, entity type, and reference name.
Repeated bindings to the same reference across targets or categories share that finding.
Keep separate findings for separate environments because lookup context can differ.

Use every distinct participating candidate as a `Location(path, 1, 1)`.
Use the first ordered candidate as the primary location.
File positions describe filename conflicts, not an invalid first YAML key.
The `key` is a generic entity type and `scope` is the environment's full name.

Message template:

```text
The same {entity type} reference name is defined at multiple scopes for environment {environment}.
```

Hint:

```text
Use distinct reference names and update the bindings, or keep the definition at one scope.
```

For ParameterSets, append:

```text
ParameterSet fragments can merge during generation; this finding checks the naming standard.
```

File paths remain visible. Do not promise filename redaction or expand the output contract of other rules.
Sort findings deterministically by environment, entity type, and candidate paths.

## Implementation design

Add `rules/int3.py` with the existing rule interface:

```python
def check(index: RepoIndex, connections: Connections | None = None) -> list[Finding]:
    ...
```

Use `compute_connections(index)` only when the caller does not supply connections.
Keep binding iteration, candidate enumeration, physical deduplication, and finding construction private to this rule.
Reuse the existing directory constants, stem parsing, model types, and safety conventions.
Do not import private INT-2 checker methods or expand `Connections.selected_paths` with hidden candidates.

Register INT-3 in `engine.py`, `rulemeta.py`, `rule_config.py`, and `report.py`.
The console has 19 rule headings. Three naming rules remain disabled by default.
The HTML renderer continues to use shared rule metadata and finding locations.

## Acceptance tests

Use real temporary repositories and assert rule findings, locations, metadata, and output text.
Each case below defines an observable behavior, independent of helper structure.

| Case                                                               | Expected INT-3 result                                  |
| ------------------------------------------------------------------ | ------------------------------------------------------ |
| Each of the four types defined at environment and cluster scopes   | One finding with both files                            |
| Each type defined at cluster and repository scopes                 | One finding with both files                            |
| A reference defined at all three scopes                            | One finding with three files                           |
| Equal stems with `.yml` and `.yaml` at different scopes            | One finding                                            |
| Different stems with equal internal names                          | No finding                                             |
| One scope, including multiple matching files                       | No finding                                             |
| Unreferenced duplicate files                                       | No finding                                             |
| Same name in a sibling environment or another cluster only         | No finding                                             |
| Repeated references across targets and categories                  | One finding per environment and type                   |
| Two consuming environments with the same conflict                  | One finding per environment                            |
| Same Credential ID in differently named bound files                | No filename conflict                                   |
| ParameterSets with disjoint keys at environment and cluster scopes | Finding without claiming a file is ignored             |
| Cluster replacement of a repository ParameterSet                   | Finding includes the hidden repository file            |
| Empty or malformed candidate YAML                                  | Filename conflict remains reportable                   |
| Jinja-only or dynamic reference                                    | No INT-3 finding                                       |
| Shared Template Variable Inventory fallback                        | Correct scope and no duplicate physical locations      |
| Lower-priority type directories at the same scope                  | No artificial cross-scope conflict                     |
| File alias to the same physical target at two scopes               | No duplicate-definition finding                        |
| External, `.git`, broken, or cyclic symlink candidate              | No unsafe access or false candidate                    |
| Directory enumeration failure                                      | Generic skip note, no crash                            |
| Secret values and IDs in a participating Credential file           | Neither appears in INT-3 output                        |
| INT-3 disabled                                                     | No check invocation or findings, reports show Disabled |
| CLI with a violation                                               | Console and HTML show INT-3, exit code remains 0       |

Run regression tests for connections, effective merging, INT-2, and existing rules.
Check that adding INT-3 findings does not alter other rules' findings on the same fixtures.
