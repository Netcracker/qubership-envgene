# envgene-linter: первый цикл PLACE-1

Отбор проверяемых файлов определяется более поздним общим [правилом подключённости](../2026-09-11-connected-only-design.md).

Ниже сохранены решения первого цикла, включая формат отчёта и исключения. Актуальное поведение описано в [алгоритме PLACE-1](../../../algorithms/ru/place1.md) и [Effective Set](../../../algorithms/effective-set.md). В частности, теперь проекции отбирают файлы, выбранные при наличии всех слоёв: исключение слоя не должно возвращать затенённый файл.

Статус на момент проектирования: принят\
Английская версия: [../2026-09-01-place1-design.md](../2026-09-01-place1-design.md)

## Цель

Линтер instance-репозиториев EnvGene создаётся заново, правило за правилом. Этот цикл даёт работающую команду `envgene-linter check <repo>`, которая выводит замечания PLACE-1 в stdout.

PLACE-1 (SHOULD): задавать значение на самом общем слое, где оно одинаково для участников; на более конкретных слоях переопределять его только при настоящем различии. В этом цикле слои — **репозиторий**, **кластер**, **окружение**. Слой шаблона не входит в проверку.

## Почему так

PLACE-1 не сводится к сравнению двух файлов. EnvGene объединяет ParameterSet. Чтобы замечание было обоснованным, нужно знать итоговое значение для окружения, слой-источник и окружения, использующие данную область параметров. Поэтому первый цикл реализует весь путь: обнаружение файлов (discovery) → Effective Set → PLACE-1 → консольный отчёт.

При расхождении документов и кода приоритет имеет **генератор на `feature/modern-toolset`**, затем `docs/configuration-standard.md`. Предыдущий `envgene-lint` — черновик, а не нормативное описание. Формулировка «первое найденное совпадение» в `docs/envgene-objects.md` относится к credentials и ресурсным профилям, а не к объединению ParameterSet.

Исходные функции генератора в локальном репозитории `/home/andy-/Work_Folder/Qubership/qubership-envgene`, ветка `feature/modern-toolset`:

- Подготовка файлов: `scripts/build_env/main.py` → `prepare_folders_for_rendering`.
- Порядок применения: `scripts/build_env/build_env.py` → `sort_paramsets_with_same_name`.
- Привязки: в том же файле `envSpecificParamsets`, `envSpecificE2EParamsets`, `envSpecificTechnicalParamsets`.
- Объединение: `modules/envgene/envgenehelper/collections_helper.py` → `dict_merge`.

## Вне этого цикла

- Слой шаблона (`from_template`, `--templates`).
- Cloud Passport в Effective Set (отложено до PLACE-4). До этого повтор паспортного ключа в ParameterSet может давать PLACE-1.
- Вычисление `*.yml.j2` и `*.yaml.j2`: файл пропускается с заметкой.
- PLACE-2…PLACE-10, NAME, SEC, INT, VAL, TPL.
- JSON/HTML-отчёты, baseline, `--strict`, `--min-envs`, комментарии `[EXCEPTION …]`, автоисправление.
- Запуск генератора EnvGene в CI.

## Архитектура

Пакет Python — `envgene_linter`. Шесть модулей с отдельными обязанностями:

| Модуль | Отвечает за | Не отвечает за |
| --- | --- | --- |
| `discovery` | Обход `environments/`, индекс кластеров, окружений, файлов ParameterSet и привязок `env_definition` | Объединение значений |
| `yamlio` | Чтение YAML и позиции ключей | Типы объектов EnvGene |
| `effective` | Effective Set одного окружения и происхождение значений | Правило PLACE-1 |
| `rules/place1` | Рекомендации переноса окружение → кластер и кластер → репозиторий | Вывод отчёта |
| `report` | Форматирование консольного отчёта | Вычисление замечаний |
| `cli` | Связывание этапов командой `envgene-linter check <repo>` | Логику правил |

Поток данных: путь репозитория → `Index` → три проекции Effective Set для каждого окружения → `Finding[]` → текст.

## Обнаружение файлов

Instance-репозиторий — каталог с `environments/`. Если его нет, обнаружение завершается с кодом 2.

Проверяемое расположение:

- Репозиторий: `environments/parameters/*.yml|yaml`.
- Кластер: `environments/<cluster>/parameters/*.yml|yaml`.
- Окружение: `environments/<cluster>/<env>/Inventory/parameters/*.yml|yaml`.
- Определение окружения: `environments/<cluster>/<env>/Inventory/env_definition.yml`.

Имя ссылки на ParameterSet — имя файла без `.yml`, `.yaml` или `.json` и завершающего `.j2`, если оно есть. Discovery индексирует и непривязанные файлы, но Effective Set применяет только файлы, названные в привязках.

Привязки находятся под `envTemplate` в `env_definition.yml`:

| Поле | Категория |
| --- | --- |
| `envSpecificParamsets` | deploy |
| `envSpecificE2EParamsets` | e2e |
| `envSpecificTechnicalParamsets` | technical |

Каждое поле сопоставляет цель со списком имён ссылок. Цель `cloud` обозначает объект Cloud; любой другой ключ — namespace. В этом цикле цели не сверяются со сгенерированным деревом `Namespaces/`: каждая цель образует область проверки.

Имена кластеров и окружений берутся из каталогов под `environments/`, а не из `inventory.environmentName` или `inventory.cloudName`.

Без репозитория шаблонов учитываются только `envSpecific*`. Набор, который подключался бы только массивом шаблона, не входит ни в одну область. Предполагаемые привязки шаблонов не создаются.

Следующие каталоги не считаются кластерами: `parameters`, `resource_profiles`, `rp_override`, `Profiles`, `credentials`, `Credentials`, `shared-credentials`, `configuration`, `configurations`, `shared_template_variables`, `shared-template-variables`, `cloud-passport`, `cloud-passports`. Внутри кластера эти же имена, а также `app-deployer` и `cloud-deployer`, не считаются окружениями.

Jinja-файлы ParameterSet (`*.yml.j2`, `*.yaml.j2`) индексируются как пропущенные и не вычисляются.

## Effective Set

**Лист** — отдельное значение параметра по пути ключей. **Происхождение** (`provenance`) — исходный файл, слой и позиция YAML. **Site** означает слой репозитория. **Проекция** — результат объединения, ограниченный указанными слоями.

Вход: индекс репозитория и одно окружение. Выход: для каждой **области** (`scope`) карта «путь листа → `{value, provenance}`».

Область — цель (`cloud` или имя namespace) × категория (`deploy`, `e2e`, `technical`). Если ParameterSet содержит `applications[].parameters`, имя приложения дополнительно разделяет области, как при обработке этих карт генератором. Окружение без привязки к данной цели и категории не использует такую область и не участвует в её проверке PLACE-1.

### Подготовка файлов без шаблона

Для имени ссылки генератор копирует:

1. Файлы репозитория из `environments/parameters/` в общий плоский временный каталог.
2. Файлы кластера из `environments/<cluster>/parameters/` в **тот же** каталог. При совпадении полного имени кластерный файл **целиком заменяет** файл репозитория (`copy_path` / `copy2`).
3. Файлы окружения из `Inventory/parameters/` в `from_instance/`; поэтому второй файл с тем же именем сохраняется.

Сравнивается полное имя файла: `.yml` и `.yaml` — разные имена, оба файла могут применяться.

### Порядок применения

`sort_paramsets_with_same_name` использует ключ сортировки `(tier, filePath)`:

- `tier = 0`: путь содержит `from_template`, `from_peer_template` или `from_origin_template`; в этом цикле не используется.
- `tier = 2`: путь содержит `from_instance`.
- `tier = 1`: остальные файлы, то есть общий каталог репозитория и кластера.

Поздние записи переопределяют ранние.

### `dict_merge(a, b)`

- Если хотя бы один аргумент не словарь, возвращается `a` при `b is None`, иначе `b`. Скаляры и списки заменяются целиком.
- Если оба аргумента — словари, объединяются их ключи, а общие ключи обрабатываются рекурсивно. `None` в `b` сохраняет прежнее значение `a`.

Источником листа считается последний файл, который задал его при объединении, в том числе явно повторил прежнее значение. Вложенный `None`, проигнорированный `dict_merge`, не меняет происхождение листа.

### Три проекции на окружение

| Проекция | Слои | Назначение |
| --- | --- | --- |
| `full` | Репозиторий + кластер + окружение | Итоговые значения; листья, заданные окружением |
| `lower` | Репозиторий + кластер | Поиск повторов окружения; листья, заданные кластером |
| `site` | Только репозиторий | Поиск повторов кластера |

«Задан на слое L» означает, что в нужной проекции происхождение листа указывает на L.

## PLACE-1

Уровень замечания — warning (SHOULD). Минимальное число согласных участников — **2**, константа без опции `--min-envs`.

**Повтор** — более конкретный слой задаёт то же значение, что уже есть в общих слоях в той же области и по тому же пути. Сравниваем окружение с `lower`, кластер с `site`. Повторы не дают PLACE-1: это предмет PLACE-2.

### Окружение → кластер

Для каждого кластера отдельно:

1. Вклад окружения — листья `full`, заданные на слое окружения и не являющиеся повторами относительно `lower`.
2. Участники области — окружения, у которых в этой области остался хотя бы один лист вклада. Одной привязки к области недостаточно для участия.
3. Замечание выдаётся, если участников не меньше двух и все они задают один и тот же путь с одним и тем же значением.

Окружение без оставшегося вклада в области не участвует. Например, два окружения с `LOG_LEVEL` могут согласоваться, если третье ничего не вносит. Если третье вносит другой ключ этой области, но не `LOG_LEVEL`, оно участвует и препятствует замечанию по `LOG_LEVEL`. Перенос в кластерный ParameterSet затрагивает только объекты, подключающие этот ParameterSet.

Одного окружения недостаточно. Разные значения не дают замечания. Если все окружения, использующие область, одинаково переопределили устаревшее значение кластера, это PLACE-1: общее значение нужно обновить на кластере.

### Кластер → репозиторий

1. Пропустить кластеры без окружений: их ParameterSet никто не использует.
2. Вклад кластера — листья `lower`, заданные кластером и не являющиеся повторами относительно `site`. Если собранные значения, заданные кластером, различаются между окружениями по одному пути, этот путь исключается.
3. Участники области — кластеры с оставшимся вкладом в этой области.
4. Замечание выдаётся, если таких кластеров не меньше двух и все задают один путь с одним значением.

### Замечание

Основная позиция берётся у первого участника после сортировки имён:

- `rule`: `PLACE-1`.
- `path` и `line`: файл и строка соответствующего листа.
- `severity`: warning.
- `key`, `scope`: ключ и область; для переноса из окружений — кластер и область, для переноса из кластеров — `repository` и область.
- `message`: кто согласен, какое значение общее и почему оно должно быть на более общем слое.
- `hint`: перенести ключ в `environments/<cluster>/parameters/` или `environments/parameters/` и удалить копии.
- `related`: позиции остальных участников.

## Консольный отчёт

Один заголовок правила, затем блок на каждое замечание:

```text
PLACE-1
<path>:<line>
warning
<message>
<hint, включая связанные пути>
```

Между замечаниями пустая строка. Если замечаний нет:

```text
PLACE-1
No findings
```

Заметки о пропущенных Jinja и нечитаемых YAML выводятся после отчёта в stderr, отдельно от блоков PLACE-1.

## Ошибки и коды выхода

| Ситуация | Код | Вывод |
| --- | --- | --- |
| Есть предупреждения | 0 | Отчёт в stdout |
| Нет замечаний | 0 | `PLACE-1` и `No findings` |
| Нет `environments/` или некорректны аргументы команды | 2 | Ошибка в stderr |
| Не читается отдельный YAML | 0, если остальная проверка завершилась | Файл пропускается; заметка в stderr |

В этом цикле предупреждения не приводят к ошибке CI; `--strict` отсутствует.

## Тестирование

Тесты пишутся вместе с алгоритмом:

1. **`dict_merge` и подготовка файлов:** вложенные карты, замена списков, сохранение значения при `None`, полная замена одноимённого файла репозитория кластерным, сохранение файла окружения в `from_instance`, одновременное применение `.yml` и `.yaml`, порядок `(tier, path)`.
2. **Синтетические репозитории PLACE-1:** одинаковые значения окружений → одно замечание; разные значения или одно окружение → нет; третье непривязанное окружение не мешает; повтор общего значения → нет; одинаковое переопределение устаревшего значения кластера → замечание; одинаковые кластерные значения двух кластеров → перенос в репозиторий; разные кластерные значения → нет.
3. **Примеры репозиториев** `testdata/place1/ok` и `testdata/place1/not-ok` с обычной структурой instance-репозитория.
4. **Эталон Effective Set:** небольшой результат генерации в `testdata/golden/`, скопированный из `qubership-envgene` на `feature/modern-toolset` с комментарием о происхождении. Тест всегда сравнивает с этим сохранённым результатом; генератор не запускается.

## Ограничения процесса

- До завершения цикла описать каждый алгоритм: сначала в этой спецификации, затем в `docs/algorithms/`.
- Если генератор и стандарт оставляют несколько вариантов поведения, уточнить решение, а не переносить молча поведение `envgene-lint`.
- Следующий цикл начинается после работающего `check` с PLACE-1, успешных тестов и появления документов алгоритмов. Кандидат — PLACE-2, который повторно использует Effective Set для поиска повторов и настоящих изменений.
