Стандарт: NAME-1 SHOULD — объединить ключи, которые действительно обозначают одно понятие, под одним каноническим именем. Одинаковые значения сами по себе не доказывают, что ключи взаимозаменяемы. В этом цикле выдаём только информационный результат **Information / Review**, без автоматического исправления и без указания ИИ исправлять ключи.

## Термины и чтение документа

- **ParameterSet:** YAML-файл с параметрами.
- **RepoIndex:** индекс файлов, кластеров и окружений, построенный при обнаружении содержимого репозитория (discovery).
- **Finding:** отдельный результат проверки в отчёте. TYPE задаёт его тип, ACTION — рекомендуемое действие.
- **Effective Set:** итоговый набор параметров после объединения слоёв.

Разделы об интеграции, порядке правил и тестах описывают цикл разработки на дату документа, а не полный состав текущего линтера. `SHOULD` обозначает рекомендацию стандарта; конкретные типы результатов указаны ниже.

## Зачем

`check` пишет NAME-1, когда в репозитории экземпляра EnvGene **разные имена ключей** имеют одну и ту же непустую строку. На странице TYPE **Information**, ACTION **Review**. Человек (или позже правило для ИИ) смотрит и не трогает ключи, пока не ясно, что это одно понятие для одного потребителя.

## Простыми словами

Три ключа Kafka, один адрес брокера → один finding, все файлы и все ключи в списке. Одно и то же имя ключа в десяти файлах — не NAME-1 (это то же имя). Имя пользователя и пароль с одинаковым значением-заглушкой не становятся обозначениями одного понятия.

## Что не делаем

- Автоматическое исправление или объединение ключей
- Минимальная длина
- Смотреть env_definition, Cloud Passport, не-paramset YAML
- Effective Set (слои не объединяем)
- NAME-2…NAME-9
- `--rules`, JSON, `--strict`

## Алгоритм

Вход: только `RepoIndex`. `compute` не вызываем.

### Файлы

Все `ParamsetFile` в индексе (repository, cluster, environment) без Jinja и без ошибки чтения. Непривязанные файлы (orphan) **входят в историческую область проверки**; сейчас они исключены по правилу подключённости выше. Passport и `env_definition` не смотрим.

### Листья

Из каждого файла:

- `parameters` — `yamlio.leaves`, только непустые строки
- каждый `applications[i].parameters` — то же; имя в отчёте `{appName}.{dotted}`

В списки не спускаемся. Вложенные словари обходим на любой глубине. Числа, логические значения, null и `""` пропускаем.

Имя ключа — полный путь из частей, разделённых точками (`NESTED.KAFKA_URL` ≠ `KAFKA_URL`).

### Группы

В одну группу входят вхождения с точно совпадающим строковым значением.

Важны **разные имена**, не число файлов. Одно имя во многих файлах → нет finding.

Затем исключаем пары ключей имени пользователя и пароля с этим значением. Пара образуется, если последние части двух имён имеют одинаковый префикс перед парными суффиксами:

| суффикс | партнёр |
| --- | --- |
| `_USER` | `_PASSWORD` или `_PASS` |
| `_USERNAME` | `_PASSWORD` / `_PASS` |
| `_PASSWORD` / `_PASS` | `_USER` / `_USERNAME` |

Смотрим **последний сегмент** пути, разделённого точками, без учёта регистра (как в старом линтере). Родительские части пути могут различаться. Например, `db.POSTGRES_USER` и `app.POSTGRES_PASSWORD` образуют пару, а `POSTGRES_USER` и `REDIS_PASSWORD` — нет. Обе стороны всех найденных пар исключаются одновременно; после этого должно остаться не менее двух разных имён.

### Finding

Один результат проверки на каждую оставшуюся группу одинаковых значений.

| Поле | Значение |
| --- | --- |
| `rule` | `NAME-1` |
| `severity` | `Severity.INFORMATION` (`information`) |
| `issue_type` | `Information` |
| `action` | `Review` |
| `path` / `line` / `column` | первое вхождение (сортировка: относительный путь файла, затем имя ключа) |
| `locations` | все вхождения группы |
| `key` | первое имя ключа |
| `scope` | `repository` |
| `related` | отсортированные уникальные имена |
| `message` | `Keys {k1}, {k2}, … share the value {value!r}.` |
| `hint` | `Review whether they mean the same concept for the same consumer. Do not collapse them unless that is intended.` |

Имена в `message` / `related` отсортированы.

## Тесты

- Три ключа Kafka, одна строка, один файл → один finding; в `related` все три; Information / Review; `locations` = 3
- Вложенность: `outer.KAFKA_URL` и `BOOTSTRAP_SERVERS` с одинаковым строковым значением → finding
- Одно имя в двух файлах, одно значение → нет NAME-1
- `POSTGRES_DBA_USER` / `POSTGRES_DBA_PASSWORD` с одинаковым строковым значением → нет finding
- Только `""` / int / bool → нет finding
- Orphan с двумя алиасами → finding
- Jinja пропускаем
- `applications[].parameters` → `{appName}.{key}`
- В консоли блок `NAME-1`; при finding — `information` и оба пути, если два файла
- HTML: `NAME-1: Different keys may name the same concept`
- Тесты PLACE-* должны проходить; точные строки «No findings» в консоли обновляем (появился блок NAME-1)
