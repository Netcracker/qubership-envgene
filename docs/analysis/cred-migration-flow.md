# Credential Migration Flow

## Assumptions

1. One Secret Store per repository - a single `default_store` covers all credentials in the repo.
   Since the store is fixed and default, no cred entry carries a `secretStore` field.
2. Repository already uses the No-CMDB flow - deployer credentials are out of migration scope.
3. Migration processes SOURCE credential files only. Generated env-scoped files
   (`<env>/Credentials/credentials.yml`) are marked for deletion - they are regenerated by env-gen
   post-migration with `type: external` entries. See "Scope of migration" below. Consequence:
   consolidation problems for cred entries within a single source do not arise. Cross-source
   same-cred-id collisions surface as apply warnings for operator review.
4. Git-tracked credential values do NOT change between plan generation and apply execution.
   Operator must not commit to cred files during this window.
5. Migration does NOT handle credential macros in `technicalConfigurationParameters` (SEC-3
   violations). They remain as `${creds.get(...)}` - a residual violation post-migration. Proper
   fix requires removing the cred macro from the template and setting the value from the instance
   repo instead. Complex and low-priority for this iteration.

## Gaps

Known gaps in the target design that this document names but does not yet resolve:

- **`<ns>` in env-tier `remoteRefPath`** - target default is `/<cluster>/<env>/<ns>`,
  but Credential Template Jinja context has no `<ns>` variable at cred authoring time. Author
  cannot template `{{ current_env.namespace }}` because a cred definition is not bound to a
  specific namespace during templating. Until resolved, migration composes paths without `<ns>`
  by default. Operator uses `remoteRefPath` override for per-ns granularity when needed.
- **`create` boolean vs 3-value semantics** - current EnvGene has a boolean `create` field
  (`true` writes when absent, `false` or omitted verifies presence). Target extension: promote to
  3-value enum (`create` / `verify` / `skip`) to model provider-generated creds (consul-bootstrap,
  k8s SA), where the provider populates the value at install and a capture script pulls it into
  the Store post-install. `skip` semantics are not supported today. Operator arranges capture
  out-of-band and uses `create: false` + `writeToStore: false` as a workaround in the plan.

## Credential types

Three credential tiers, distinguished by scope and authoring location:

### `passport-tier`

Cluster-wide credentials, shared across all envs on the cluster.

- **Authored in**: `environments/<cluster>/cloud-passport/*-creds.yml`
- **Default `remoteRefPath`**: `/<cluster>`
- **Default `create`**: `false`
- **Examples**: `dbaas-cluster-dba-creds`, `argocd-cred`, `keycloak-client-cred`,
  `consul-bootstrap-token`

### `env-tier`

Env-scoped credentials specific to one environment.

- **Authored in**:
  - Credential Template (`templates/external-credentials/<descriptor-stem>.yml.j2`) - Template
    Repository. One file per Template Descriptor. Filename stem matches descriptor stem
    (`dev.yaml` descriptor → `dev.yml.j2` Credential Template).
  - Env-scoped Shared Credential files (`environments/<cluster>/<env>/Inventory/credentials/*.yml`)
    - Instance Repository
- **Default `remoteRefPath`**: `/<cluster>/<env>/<ns>`
- **Default `create`**: `true`
- **Examples**: `bss-endpoint-cred`, per-env app credentials

### `external-tier`

Cross-scope credentials - not tied to a single cluster or env.

- **Authored in**:
  - Shared Credential files at repo/cluster scope: `environments/credentials/*.yml`,
    `<cluster>/credentials/*.yml` (env-scoped `<env>/Inventory/credentials/*.yml` is env-tier -
    see above)
  - System Credentials (EnvGene tooling): `configuration/credentials/*.yml`,
    `<env>/app-deployer/deployer-creds.yml`
- **Default `remoteRefPath`**: `/external`
- **`create` field**: omitted (implicit `false` - verify only)
- **Examples**: `webex-token-cred`, `pati-cred`, `cmdb-user`, `x_saas_tu_token`

`remoteRefPath` is the prefix that env-gen writes to the source. Env-gen (via
`SecretNameBuilder.buildNormalizedSecretName`) appends the normalized cred-id when composing the
final Store path, so `remoteRefPath` MUST NOT include the cred-id itself.

## Prerequisites

- EnvGene version with external credential support (includes migration script)
- DevOps toolset used by the deploy pipeline at versions that understand external credentials,
  and configured for Secret Store access.

## Migration script

Python module packaged with EnvGene. Two subcommands:

| Subcommand | Effect                                                                                     |
|------------|--------------------------------------------------------------------------------------------|
| `plan`     | Scans repo. Writes `migration-plan.yaml` artifact. Emits stdout plan-report. No writes.    |
| `apply`    | Reads `migration-plan.yaml`. Writes to Git + Secret Store. Emits stdout migration-report.  |

Invocation. Repo type is passed explicitly via `--repo=<instance|template>`; script errors if the
flag is missing.

```bash
python -m envgene.migrate plan --repo=instance
python -m envgene.migrate plan --repo=template
python -m envgene.migrate apply --repo=instance
python -m envgene.migrate apply --repo=template
```

If the repo has SOPS-encrypted cred files, the SOPS key MUST be provided via the `SOPS_AGE_KEY`
env var (same variable used by env-gen and `external-cred-provision`) to both `plan` and `apply`.
The script decrypts sources on read. If the var is not set, the script errors on the first
encrypted file.

The key is used in-memory only - never written to disk, never committed, never echoed in logs or
reports.

Instance-repo `apply` also needs Secret Store auth. The script reads `secret-stores.yml`,
determines which store types are in use, and requires the matching env vars to be present at
invocation - pre-flight fails fast with a clear message if any required var is missing:

| Store type | Required env vars                                                  |
|------------|--------------------------------------------------------------------|
| Vault      | `VAULT_ADDR`, `VAULT_TOKEN`                                        |
| OpenBao    | `VAULT_ADDR`, `VAULT_TOKEN`                                        |
| GCP        | `GOOGLE_APPLICATION_CREDENTIALS`                                   |
| AWS        | `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION` |
| Azure      | `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`        |

Values are read only from the process environment - no flag or file input for auth, matching the
`external-cred-provision` CLI convention. `plan` and Template-repo `apply` do not need these vars
(no Store I/O).

Artifacts:

- **`migration-plan.yaml`** - structured plan committed to migration branch. Editable by operator
  or AI. See "Plan artifact schema" below.
- **stdout plan-report** - decision-focused summary during `plan`. See "Plan-report sample" below.
- **stdout migration-report** - execution status during `apply`. See "Migration-report sample" below.
- **stderr progress log** - apply streams per-file progress lines to stderr (`tail -f`-able during
  long runs on large repos).

### Scope of migration

Migration operates on SOURCE credential files. Generated files and out-of-scope files are
collected in the plan's `to_delete:` section and removed during apply. Consumer files, Secret
Store config, and env definitions are read or updated as needed.

Sources define credentials once. The same cred-id appears repeatedly in generated env files
because env-gen expands sources into per-env forms. Processing only sources means each cred is
migrated once, not N times per env. Each source has one canonical value. If the same cred-id
appears in different sources (for example per-env Shared cred files) with different values, apply
writes each to its own Store path and surfaces a warning for operator review.

#### Credential source files

- **Credential Template** - `templates/external-credentials/<descriptor-stem>.yml.j2`, one file
  per Template Descriptor. Created or extended by apply from the plan (discovered from consumer
  templates transitively through the descriptor's tree). Source of truth for env-tier defaults.
- **Cloud Passport creds** - `environments/<cluster>/cloud-passport/*-creds.yml`. Rewrite + write
  plaintext to Store.
- **Shared Credential files** at three scopes:
  - Repo: `environments/credentials/*.yml`
  - Cluster: `environments/<cluster>/credentials/*.yml`
  - Env: `environments/<cluster>/<env>/Inventory/credentials/*.yml`

  Rewrite + write plaintext to Store. If orphaned (not referenced by any env definition):
  **Delete** as unused.
- **System Credentials** - `configuration/credentials/credentials.yml`, other root cred files.
  Rewrite + write plaintext to Store.
- **Env-scoped generated creds** - `environments/<cluster>/<env>/Credentials/credentials.yml`.
  **Delete** - regenerated by env-gen post-migration with `type: external` entries composed from
  sources.
- **Deployer creds** - `environments/<cluster>/<env>/app-deployer/deployer-creds.yml`.
  **Delete** - out of scope per No-CMDB (Assumption 2).

#### Credential consumer files

Consumer files are not credential files, but reference credentials via macros or Built-in fields.
Migration handles the two forms differently:

- **Macros** (`${creds.get(...)}`, `${envgen.creds.get(...)}`, `${cmdb.creds.get(...)}`) in
  `deployParameters` / `e2eParameters` / ParameterSets - rewritten to `$type: credRef` +
  `credId` + optional `property`.
- **Built-in cred field refs** (`credentialsId`, `defaultCredentialsId`, `tokenSecret`,
  `credential`) - untouched. They stay plain `credId` strings. The underlying cred definition is
  what changes to `type: external`.

Consumer file locations scanned:

- **Template Repository**:
  - Environment Template files: `templates/env_templates/<solution>/cloud.yml.j2`,
    `namespace*.yml.j2`, `tenant.yml.j2`
  - ParameterSet files: `templates/parameters/<area>/*.yml`
- **Instance Repository**:
  - Cloud Passport main files: `environments/<cluster>/cloud-passport/<cluster>.yml`
  - ParameterSets: `environments/<cluster>/<env>/Inventory/parameters/*.yml`,
    `environments/<cluster>/parameters/*.yml`, `environments/parameters/*.yml`
  - System-related config files with cred macros: `configuration/integration.yml`,
    `configuration/registry.yml`, `environments/<cluster>/<env>/app-deployer/deployer.yml`
  - Artifact/Registry Definitions with Built-in `credentialsId` refs (kept as strings):
    `configuration/artifact_definitions/*.yml`, registry definition files

#### Ancillary files

**Updated by apply**:

- Template Descriptor per env template - apply adds `external_credential_template` field pointing
  to the per-descriptor Credential Template file created during T3 (template phase only)

**Created by operator during migration** (outside script scope, referenced from Flow):

- `configuration/secret-stores.yml` - Secret Store configuration (created in I1)

**Read but not modified** (used to compute migration scope):

- `environments/<cluster>/<env>/Inventory/env_definition.yml` - env definitions with template
  bindings. Source of "which envs exist and which templates they bind to"

### `migration-plan.yaml` schema

Plan groups credentials by source file for readability at scale. Each source file lists its own
`to_review:` (ambiguous) and `to_confirm:` (default-accepted) credentials.

Top-level sections:

- `credentials:` - list of source-file groups. Each group has `to_review:` and `to_confirm:` maps
  keyed by cred-id
- `to_delete:` - files apply will delete (generated env-scoped + out-of-scope)

At scale, operator focuses on `to_review:` entries within each file (short). The `to_confirm:`
entries under each file can be scrolled past unless operator wants to override a default.

#### Instance-repo plan example

```yaml
repo_type: instance
generated_at: 2026-08-05T12:00:00Z

# Credentials grouped by source file. Each cred-id is a key; value is an editable-fields map.
credentials:
  - sourceFile: environments/prod-cluster/cloud-passport/prod-cluster-creds.yml
    to_review:
      arango-db-creds:
        remoteRefPath: /prod-cluster/env-a/bss   # env-gen appends normalized cred-id
        create: true                             # true = write on absent; false = verify presence
        writeToStore: true                       # true (default) writes value + rewrites Git; false rewrites Git only
        suggestions:
          - "if platform-shared: set remoteRefPath to /prod-cluster and create=false (promotes to passport-tier shape)"
    to_confirm:
      dbaas-cluster-dba-creds:
        remoteRefPath: /prod-cluster
        create: false
        writeToStore: true
      consul-bootstrap-token:
        remoteRefPath: /prod-cluster
        create: false                            # gap: skip semantics not supported; provider populates at install
        writeToStore: false                      # workaround: migration does not write; capture handled out-of-band

  - sourceFile: environments/credentials/shared-ci-creds.yml
    to_review: {}
    to_confirm:
      webex-token-cred:
        remoteRefPath: /external
        create: false
        writeToStore: true

  - sourceFile: configuration/credentials/credentials.yml
    to_review: {}
    to_confirm:
      pati-cred:
        remoteRefPath: /external
        create: false
        writeToStore: true

# Files apply will delete, grouped by reason
to_delete:
  generated_env_credentials:                 # regenerated by env-gen post-migration
    - environments/prod-cluster/env-a/Credentials/credentials.yml
    - environments/prod-cluster/env-b/Credentials/credentials.yml
    # ... (one per env)
  unused_shared_credentials:                 # Shared cred files not referenced by any env definition — orphaned
    - environments/prod-cluster/env-legacy/Inventory/credentials/inventory_generation_creds.yml
    # ... (only orphaned files; used files are migrated as sources)
  deployer_credentials:                      # out of scope per No-CMDB
    - environments/prod-cluster/env-a/app-deployer/deployer-creds.yml
    - environments/prod-cluster/env-b/app-deployer/deployer-creds.yml
```

#### Template-repo plan example

```yaml
repo_type: template
generated_at: 2026-08-05T12:00:00Z

credentials:
  # One group per Template Descriptor. Stem matches (`bss.yaml` descriptor → `bss.yml.j2`).
  - sourceFile: templates/external-credentials/bss.yml.j2
    to_confirm:
      app-db-cred:
        remoteRefPath: "{{ current_env.cloud }}/{{ current_env.name }}/{{ current_env.namespace }}"  # env-tier default; env-gen appends credId
        create: true
      platform-integration-cred:
        remoteRefPath: "{{ current_env.cloud }}/{{ platform_integration_cred_scope }}"  # operator override
        create: false
```

**Editable fields per credential entry**: `remoteRefPath`, `create`, `writeToStore` (instance
only). The cred-id itself is the map key and is not editable (rename in the source file instead
if needed). Cred type is not carried in the plan - apply reads it from the source file at apply
time.

**`properties` on the rewritten cred entry** is derived by apply from the source cred entry's
`data` keys. Multi-field creds get `properties: [{name: <key>}, ...]`. Single-value creds get no
`properties` block. Not in the plan artifact.

**Template-phase specifics**: no Store writes at template migration. `writeToStore` field is
neither set nor read for template-repo plans - values migrate per env during Instance-repo apply.
`remoteRefPath` is always a Jinja string that env-gen renders per env when the template is used.
Migration composes the env-tier default
(`"{{ current_env.cloud }}/{{ current_env.name }}/{{ current_env.namespace }}"`). Operator may
replace it with any Jinja template.

### Plan actions

#### Template repo

`python -m envgene.migrate plan --repo=template` performs, in order:

1. For each Template Descriptor `templates/env_templates/<stem>.yaml` (or `.yml`):
   - Parse the descriptor. Follow references from `tenant`, `cloud`, `composite_structure`, and
     `namespaces[].template_path`. Descriptor-level `parametersets` field is ignored (rudiment).
   - Scan each referenced template for `${creds.get(...)}` macros, hash-macros, and Built-in cred
     field references.
   - Extract `deployParameterSets` and `e2eParameterSets` names from the same templates.
     `technicalConfigurationParameterSets` is skipped per Assumption 5.
   - Resolve paramset names to files via inner `name:` field in `templates/parameters/**/*`.
     Scan resolved paramset files for the same cred forms.
   - If `templates/external-credentials/<stem>.yml.j2` exists, merge its existing cred entries.
   - Emit one plan group per descriptor. The `sourceFile` points at
     `templates/external-credentials/<stem>.yml.j2` (existing or planned). Apply creates or
     extends that file.
2. Classifies each cred entry. Default is env-tier: `remoteRefPath` as env-gen Jinja
   (`"{{ current_env.cloud }}/{{ current_env.name }}/{{ current_env.namespace }}"`; env-gen
   appends the normalized cred-id) and `create: true`. Infers cred type from usage: `.username`
   / `.password` macros → `usernamePassword`; `.secret` macros and Built-in field references →
   `secret`. Cred-ids matched by shadow-platform heuristics (see "Classification algorithm")
   receive passport-tier defaults instead (`remoteRefPath: "{{ current_env.cloud }}"`,
   `create: false`) plus a suggestion warning that the cred looks like a Cloud Passport cred.
3. Runs shadow-platform-integration heuristics (see "Classification algorithm" below)
4. Writes `migration-plan.yaml`
5. Emits stdout plan-report (see "Plan-report sample" below)

#### Instance repo

`python -m envgene.migrate plan --repo=instance` performs, in order:

1. Scans Cloud Passport `*-creds.yml`, Shared Credential files (repo/cluster/env scope), and
   System Credentials
2. Classifies each cred entry: assigns tier from file location, composes default `remoteRefPath`
   per tier + default `create` per tier
3. Runs shadow-platform-integration heuristics (see "Classification algorithm" below)
4. Identifies files for deletion: generated env-scoped `Credentials/credentials.yml`, unused
   Shared credential files (not referenced by any env definition - see "Orphaned Shared
   credential detection" below), `app-deployer/deployer-creds.yml`
5. Writes `migration-plan.yaml`
6. Emits stdout plan-report (see "Plan-report sample" below)

### Apply actions

#### Template repo

`python -m envgene.migrate apply --repo=template` performs, in order:

1. Reads `migration-plan.yaml`
2. Validates internal consistency (`remoteRefPath` shape ↔ `create` implications) - warns on
   mismatch
3. For each descriptor's cred entries in the plan:
   - If `templates/external-credentials/<descriptor-stem>.yml.j2` does not exist, create it.
   - Add or update each cred entry as `type: external` + `remoteRefPath` + `create` + `properties`.
     Properties come from the source `data` keys when migrating an existing entry, or are inferred
     from macro-usage form for auto-discovered cred-ids (`.username`+`.password` → multi-field;
     `.secret` or Built-in ref → single-value). Removes any `data` field. No Store writes because
     template creds are placeholders; per-env values migrate during Instance-repo apply. Warns for
     `envgeneNullValue` placeholders.
4. Scans consumer files (Environment Template files, ParameterSet templates) for macros
   (`${creds.get(...)}`, `${envgen.creds.get(...)}`, `${cmdb.creds.get(...)}`) and rewrites them
   to `$type: credRef` + `credId` + optional `property`. Macros in
   `technicalConfigurationParameters` are left untouched (Assumption 5)
5. For each descriptor where a Credential Template file was created, adds the
   `external_credential_template` field to the descriptor pointing at the file (if missing).
   Convention: the created file's stem matches the descriptor's stem (`dev.yaml` →
   `dev.yml.j2`).
6. Runs post-apply verification - fails apply on any issue:
   - No `data` field remains on any cred entry (definition of done (DoD): zero cred values in Git)
   - Every cred entry has `type: external` with `remoteRefPath` present and non-empty
   - Built-in cred fields (`credentialsId`, `defaultCredentialsId`, `tokenSecret`, `credential`)
     stay plain `credId` strings
   - Every used `credId` declared in the Credential Template
   - Every touched cred / paramset / template file validates against its EnvGene schema
7. Streams per-item progress to stderr (`tail -f`-able). Emits stdout migration-report on
   completion (see "Migration-report sample" below)

#### Instance repo

`python -m envgene.migrate apply --repo=instance` performs, in order:

1. Reads `migration-plan.yaml`
2. Validates internal consistency (`remoteRefPath` shape ↔ `create` implications) - warns on
   mismatch
3. For each credential entry across all `to_review` and `to_confirm` lists - honors `writeToStore`
   flag per entry:
   - `true` (default): writes value from Git to Secret Store at `remoteRefPath`; rewrites cred
     entry in Git to `type: external` + `remoteRefPath` + optional `create` + `properties`;
     removes `data`
   - `false`: rewrites cred entry in Git only, no Store write (Store already seeded - ops
     compliance - or provider will overwrite)
   - Warns for creds with placeholder values (`envgeneNullValue`) - cannot write nothing.
     Operator must seed manually before or after apply
   - Git rewrite always happens (DoD: no cred values in Git)
4. Scans consumer files (Cloud Passport main files, env-specific `cloud.yml`, `namespace.yml`,
   `Applications/*.yml`, ParameterSets, System-related config with cred macros) for macros
   (`${creds.get(...)}`, `${envgen.creds.get(...)}`, `${cmdb.creds.get(...)}`) and rewrites them
   to `$type: credRef` + `credId` + optional `property`. Macros in
   `technicalConfigurationParameters` are left untouched (Assumption 5)
5. Deletes files listed in `to_delete:` groups (generated env credentials, unused shared
   credentials, deployer credentials)
6. Runs post-apply verification - fails apply on any issue:
   - No `data` field remains on any cred entry (DoD: zero cred values in Git)
   - Every cred entry has `type: external` with `remoteRefPath` present and non-empty
   - Built-in cred fields (`credentialsId`, `defaultCredentialsId`, `tokenSecret`, `credential`)
     stay plain `credId` strings
   - Every used `credId` declared somewhere on the resolution path
   - All files in plan's `to_delete:` are gone
   - Every touched cred / paramset / cloud / namespace file validates against its EnvGene schema
7. Streams per-item progress to stderr (`tail -f`-able). Emits stdout migration-report on
   completion

Notes (Instance repo):

- Secret Store population happens in step 3 - no separate manual provisioning step during migration
- Generated env-scoped credential files are deleted in step 5 - env-gen regenerates them
  post-migration with `type: external` entries composed from migrated sources
- Post-migration business-as-usual (BAU) credential lifecycle (who writes new values after
  migration completes) - see "Provision reference" below
- On verification failure - apply is idempotent. Operator fixes the issue and re-runs
  `envgene.migrate apply`. Use Rollback only when going back to pre-migration state.

### Implementation requirements

Guiding principle: migration reuses three existing pieces of EnvGene and adds nothing else.

#### Delegate Store writes to `external-cred-provision`

Instance-repo apply MUST delegate all Store I/O to `external-cred-provision`
(`python/external-cred-provision/`). The migration script MUST NOT open sockets to Vault / AWS /
GCP / Azure directly. Store auth env vars are a required input contract, validated by pre-flight
against `secret-stores.yml` - see "Invocation" for the per-store-type variable list.

Migration-specific overrides on top of the CLI contract:

- `strategy` is always `overwrite` - Git holds the canonical value at migration time. The plan's
  `create` field governs post-migration BAU (see "Provision reference"), not migration.
- `data` is real plaintext read from Git. `_generateValue` MUST NOT be emitted - migration
  migrates real values, never fabricates.
- `envgeneNullValue` placeholders - apply skips the Store write and logs a warning. Operator seeds
  those values out-of-band. Git rewrite still happens.

Template-repo apply has NO Store writes and does NOT invoke the CLI - per-env values migrate
later, during Instance-repo apply.

#### Reuse `envgenehelper.crypt` + `crypt_backends` for source-file decryption

Both `plan` and `apply` MUST decrypt SOPS-encrypted cred files in memory via
`envgenehelper.crypt` + `crypt_backends` - same backend selection env-gen uses, no bespoke SOPS
integration in migration. Key input is defined in "Invocation" (`SOPS_AGE_KEY` env var).

#### Reuse VALS-URI and normalization contract via a shared Python helper

The CLI-context `vals` field and the normalized secret name MUST be produced by a shared helper
(target location `envgenehelper.external_creds`) that mirrors the Java contract in
`build_effective_set_generator/.../ExternalCredUtils.java` - specifically
`buildValsUriWithoutFragment(store, normalizedName, storeId)` and
`SecretNameBuilder.buildNormalizedSecretName(remoteRefPath, credId, storeType)`.

### Classification algorithm

Classification runs in `plan` to decide tier + defaults + whether the entry lands in `to_review`
(operator attention needed) or `to_confirm` (default accepted). Signals combined, any hit routes
to `to_review`; no hit routes to `to_confirm`. `suggestions` list is populated per-signal.

Signals (all case-insensitive matching):

1. **Known Cloud Passport cred-id registry.** Explicit `frozenset` of cred-ids observed as
   top-level keys in `environments/*/cloud-passport/*-creds.yml` across real instance repos.
   Sourced from a snapshot of 25 EnvGene instance repos (104 distinct cred-ids). See
   `known_creds.py`. Exact-match on `credId` → cred is a known Cloud Passport cred; treat as
   passport-tier candidate.

2. **Known-platform-service pattern on cred-id.** Regex on `credId` (anchored, matches whole id):
   - `^(dbaas|argocd|arango|cluster|consul|keycloak|maas|vault|k8s|kube)([-_].+)?$`
   Any match → shadow-platform integration suspected. Suggestion: promote to `passport-tier` shape
   (`remoteRefPath=/<cluster>`, `create=false`).

3. **Cred-id keyword substring.** Case-insensitive substring on `credId`:
   - `cluster`, `admin`, `dba`, `root`, `superuser`, `bootstrap`, `master`
   Any match → shared-scope suspected. Suggestion: same as #2.

4. **Source-comment marker.** YAML comment on or immediately above the cred entry contains one
   of (case-insensitive):
   - `cloud passport`, `platform`, `script generated`, `manual`, `shared across envs`
   Comment content classified verbatim in the suggestion (`# cloud passport: X` → suggest
   passport-tier).

5. **Cross-namespace consumer analysis** (TODO - algorithm not specified yet). Placeholder in
   the plan skeleton; do not fire in initial implementation. See Open items.

Combining signals:

- Any signal fires → `to_review`. Template-phase plan also **flips defaults to passport-tier
  shape** (`remoteRefPath: "{{ current_env.cloud }}"`, `create: false`) and attaches a
  suggestion warning the operator that the cred looks like a Cloud Passport cred (value comes
  from Cloud Passport in the Instance repo; operator should remove from plan if so, keep only
  if EnvGene should manage this cluster-wide cred).
- No signals → `to_confirm` with tier defaults per file location.

Cross-env value hashing is intentionally out of scope for the initial implementation (see Open
items).

### Macro rewrite algorithm

Applies during `apply` to consumer files. Grammar and transformations:

#### Recognized macro forms

**Value macros** (inside YAML scalar values):

- `${creds.get('<credId>').username}` - multi-field
- `${creds.get('<credId>').password}` - multi-field
- `${creds.get('<credId>').secret}` - single-value
- `${envgen.creds.get('<credId>').X}` - alias, `envgen.` prefix stripped, then same as above
- `${cmdb.creds.get('<credId>').X}` - alias, `cmdb.` prefix stripped, then same as above

Regex (anchored to full value; whitespace tolerant around identifiers):

```text
^\s*\$\{\s*(?:envgen\.|cmdb\.)?creds\.get\(\s*['"]([\w.-]+)['"]\s*\)\.(username|password|secret)\s*\}\s*$
```

**Hash-style key macros** (legacy form, macro is the YAML key not the value):

- `#creds{<credId>, <field>}` - `<field>` is `username` / `password` / `secret`
- `#credscl{<credId>, <field>}` - cluster-scope alias, semantically equivalent
- `#credsns{<credId>, <field>}` - namespace-scope alias, semantically equivalent

Hash-style key macros MUST be recognized alongside `${...}` value macros - both are legitimate
input to migration. Reference: `python/envgene/envgenehelper/creds_helper.py::check_is_cred`.

#### Property mapping

| Macro suffix     | credRef `property` | Notes                        |
|------------------|--------------------|------------------------------|
| `.username`      | `username`         | Multi-field cred             |
| `.password`      | `password`         | Multi-field cred             |
| `.secret`        | (omitted)          | Single-value cred            |

For hash-style macros, the `<field>` argument maps identically.

#### Composite values

A macro embedded inside a larger string (for example `user=${creds.get('X').username}@host`) is
NOT rewritten because `$type: credRef` cannot express partial substitution. Apply FAILS with a
targeted error listing the file path, key path, and offending value. Operator relocates the value
composition (typically into two separate parameters) before re-running `plan` + `apply`.

#### YAML paths that are rewritten

- `deployParameters` block on Cloud, Namespace, Tenant objects
- `e2eParameters` block on Cloud, Namespace, Tenant objects
- `parameters` block inside a ParameterSet
- `applications[].parameters` inside a ParameterSet

YAML paths that are NOT rewritten (Assumption 5):

- `technicalConfigurationParameters` on any object
- ParameterSets used only through `technicalConfigurationParameterSets` (identified by their sole
  binding on the consuming object)

Built-in cred field references (`credentialsId`, `defaultCredentialsId`, `tokenSecret`,
`credential`) are NOT rewritten - they stay as plain `credId` strings by contract.

#### YAML formatting preservation

Rewrites MUST preserve source formatting: comments, blank lines, YAML anchors, aliases,
key order. Use `envgenehelper.yaml_helper` primitives (`openYaml`, `writeYamlToFile`,
`beautifyYaml`), which wrap `ruamel.yaml` round-trip mode. Do not fall back to PyYAML for
consumer-file rewrites.

### Consistency validation rules

Apply validates each cred entry in the plan before Store/Git writes. Warnings do not block;
errors abort apply before any write.

Rules (invariants; violation → warning unless marked error):

1. **`remoteRefPath` tier-shape match.** Expected prefix per tier:
   - `passport-tier` → `/<cluster>` (one path segment after `/`)
   - `env-tier` → `/<cluster>/<env>` or `/<cluster>/<env>/<ns>` (2-3 path segments)
   - `external-tier` → `/external` (one path segment, literal)
   Mismatch → warning ("path shape does not match tier default; confirm intentional override").

2. **`create: true` on `external-tier`.** Warning - external-tier defaults to `create: false`;
   `true` is unusual (external secrets typically pre-exist).

3. **`writeToStore: true` combined with `envgeneNullValue` in source data.** Warning - cannot
   write placeholder value; migration skips Store write and rewrites Git only.

4. **Missing `create` field.** Treated as `create: false` (implicit). No warning; documented
   default.

5. **ERROR: cred-id in plan not present in source file at apply time** (Assumption 4 violation).
   Aborts apply.

6. **ERROR: source cred entry already `type: external`.** Partial-migration detection - apply
   refuses to re-migrate an already-external entry. Operator resolves by removing entry from plan
   or restoring source to pre-migration state.

### Error and exit contract

Standard Linux conventions. Exit codes:

| Code | Meaning                                                                      |
|------|------------------------------------------------------------------------------|
| 0    | Success                                                                      |
| 1    | Apply failed (Store write error, Git rewrite error, verification failure)    |
| 2    | Plan invalid (schema error, unknown cred type, partial-migration detected)   |
| 3    | Pre-flight failed (missing auth env vars, missing SOPS key, dirty git tree)  |
| 130  | User interrupt (SIGINT) - see "State handling"                               |

Logs are free-text on stdout (structured reports) and stderr (per-item progress + errors). No
JSON output. Failure lines follow the pattern `[<cred-id>] FAILED: <reason>` for machine grep.

### State handling

**Plan already exists.** `plan` overwrites `migration-plan.yaml` in the current working directory
without prompting. Operator commits the plan explicitly.

**Dirty git working tree at apply.** Apply runs `git status --porcelain` before writing. If any
tracked file is modified/staged/deleted, apply aborts with exit code 3 and message listing dirty
paths. Untracked files are ignored. Operator commits or stashes before retrying.

**Multiple stores in `secret-stores.yml`.** Violation of Assumption 1. Apply exits code 3 with a
targeted error. Migration does not support multi-store repos in the initial implementation.

**Interrupted apply.** Apply is idempotent - `strategy: overwrite` on Store writes and no-op
consumer-file rewrites when already converted. Re-running apply after SIGINT/error resumes
cleanly from wherever apply left off; no state file, no resume mechanism, no partial-run
bookkeeping. Operator re-runs `envgene.migrate apply` after fixing the root cause.

**Concurrent invocations.** Not supported. Operator responsibility to serialize.

### Orphaned Shared credential detection

Algorithm for `plan` step 4 (Instance repo) - identifying Shared cred files marked to delete
because no env references them:

1. Build the set of **all declared cred-ids** across all Shared cred files (repo/cluster scope).
2. Build the set of **all referenced cred-ids** by scanning consumer files:
   - Value macros: `${creds.get(...)}`, `${envgen.creds.get(...)}`, `${cmdb.creds.get(...)}`
   - Key macros: `#creds{...}`, `#credscl{...}`, `#credsns{...}`
   - Built-in cred fields on Cloud/Namespace/Tenant/BG-domain objects (`credentialsId`,
     `defaultCredentialsId`, `maasConfig.credentialsId`, `dbaasConfigs[].credentialsId`,
     `vaultConfig.credentialsId`, `consulConfig.tokenSecret`, `Namespace.credentialsId`,
     `Tenant.credential`, `controllerNamespace.credentials`)
   - `credId` field on `$type: credRef` blocks
   - System-configuration cred refs (`configuration/integration.yml`,
     `configuration/registry.yml`, `configuration/artifact_definitions/*.yml`, registry
     definition files)
3. A Shared cred file is **orphaned** if every cred-id it declares is missing from the referenced
   set.
4. Env-scoped Shared cred files (`<env>/Inventory/credentials/*.yml`) are always considered
   env-tier and never flagged orphaned by this pass (their env context makes them referenced by
   env definition).

Reference: `docs/features/external-creds.md` describes the declaration/reference contract that
this algorithm mirrors.

### Cred type support and `properties` derivation

Apply derives `properties` from the source cred entry's `data` keys and rewrites the entry
according to type:

- **`type: usernamePassword`** - source `data: {username: X, password: Y}` → target
  `properties: [{name: username}, {name: password}]`, no `data`.
- **`type: secret`** - source `data: {secret: X}` (or scalar `data: X`) → no `properties`
  block, no `data`.

Cred types other than `usernamePassword` and `secret` (`vaultAppRole`, `sshPrivateKey`, custom)
are NOT supported by migration in the initial implementation. Apply FAILS with exit code 2 and
message `[<cred-id>] FAILED: unsupported cred type '<type>'` when encountered. Operator handles
these creds out-of-band.

### CLI output parsing

Apply parses `external-cred-provision` output to determine per-cred outcome and route Git
rewrites accordingly.

**Parsing contract:**

- Capture CLI stderr line-by-line during invocation.
- Per-cred outcome markers in the CLI log (from `provisioner.py`):
  - `[<cred-id>] created` - success
  - `[<cred-id>] overwritten` - success (migration always overwrites)
  - `[<cred-id>] skipped` - success (secret already present, no write)
  - `[<cred-id>] verified` - success (fail_if_absent hit, present)
  - `[<cred-id>] FAILED: <type>: <reason>` - failure
- CLI exit code 0 means all creds succeeded. Exit code 1 means at least one cred failed - migration
  still parses per-cred outcomes so successful creds get their Git rewrites.

**Per-cred atomicity:** for each cred-id in the plan, migration cross-references the CLI outcome
line. If the outcome is success, migration proceeds with the Git rewrite for that cred. If
failure, migration leaves the Git entry untouched and re-emits the failure in its own
migration-report.

**Dry-run:** `envgene.migrate apply --dry-run` propagates `--dry-run` to the CLI, which emits
`[<cred-id>] dry_run_ok` or `[<cred-id>] dry_run_fail: ...` per entry. Migration parses the same
markers, no Git rewrites happen.

## Flow

Two-phase migration on isolated branches. Template Repository first (publishes new template
version). Instance Repository second (points at that new version). Each phase merges after
verification.

### Phase 1 - Template Repository

Create migration branch. All changes below happen on this branch.

#### T1 - Plan

```bash
python -m envgene.migrate plan --repo=template
```

See "Plan actions" in Migration script section for what script does. Review stdout plan-report.

#### T2 - Review and edit plan

Open `migration-plan.yaml`. For each `to_review` entry: accept default or edit `remoteRefPath` /
`create`. Commit `migration-plan.yaml` to migration branch.

#### T3 - Apply

```bash
python -m envgene.migrate apply --repo=template
```

See "Apply actions" in Migration script section.

#### T4 - Build and publish template version

Run template build pipeline. Publish concrete version `<artifactId>:<version>` from the migration
branch. Do NOT merge the migration branch yet - Instance phase must succeed first (see I7).

### Phase 2 - Instance Repository

Create migration branch. Point at the new template version published in T4. All changes below
happen on this branch.

#### I1 - Configure Secret Store

Under the "one cred store per repo" assumption, define a single default store in
`/configuration/secret-stores.yml`:

```yaml
default_store:
  type: vault           # or gcp, aws, azure
  # store-specific fields (mountPath, projectId, region, vaultName)
```

Configure CI/CD variables for Secret Store authentication per store type:

| Store type | CI/CD variables                                                    |
|------------|--------------------------------------------------------------------|
| Vault      | `VAULT_ADDR`, `VAULT_TOKEN`                                        |
| OpenBao    | `VAULT_ADDR`, `VAULT_TOKEN`                                        |
| GCP        | `GOOGLE_APPLICATION_CREDENTIALS`                                   |
| AWS        | `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION` |
| Azure      | `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`        |

See [`external-creds`](/docs/features/external-creds.md) for full store configuration reference.

Also agree with Platform team the path convention for shadow-platform integrations (creds not in
CP schema) - needed for author overrides in I3.

#### I2 - Plan

```bash
python -m envgene.migrate plan --repo=instance
```

See "Plan actions" in Migration script section. Instance-phase warnings surface shadow-platform
candidates most heavily here - cross-env hashing runs against all envs in repo.

#### I3 - Review and edit plan

Same workflow as T2 - open `migration-plan.yaml`, edit `to_review` entries per suggestions,
commit plan to branch.

#### I4 - Apply

```bash
python -m envgene.migrate apply --repo=instance
```

See "Apply actions" in Migration script section.

#### I5 - Test env generation

Run env-generation pipeline against migration branch with new template version. Verify:

- Environment Instance generation succeeds
- External Credential Context built
- Effective Set generated with VALS or ESO refs, no plaintext
- Deployment contexts use expected refs

Failure indicates classification mismatch (return to I3) or a cred still absent in Store (operator
placeholder that apply warned about - seed via vault CLI + re-run).

#### I6 - Test deploy

Run actual deploy pipeline against the migration branch's Effective Set.

> [!WARNING]
> This step requires the rest of the DevOps toolset (argocd, deployer, CI runners, image build)
> at versions that understand external credentials, and configured with Secret Store access (VALS
> binary in runner images, ESO installed on cluster for `SECRET_FLOW: external-values`). See
> Prerequisites.

Verify:

- Deploy pipeline succeeds
- Deployed applications receive credential values correctly (no fallback to plaintext, no
  auth errors related to missing creds)

Failure here often indicates DevOps toolset misconfiguration (Store access, VALS/ESO integration).
Fix toolset side. Migration plan usually unchanged.

#### I7 - Merge migration branches

After successful deploy test, merge both migration branches to main:

1. Merge Template Repository migration branch (publishes migration changes as canonical template
   version)
2. Merge Instance Repository migration branch (finalizes instance state pointing at merged
   template version)

Peer review both PRs.

## Rollback

Rollback happens through git - restore repo state to pre-migration.

## Appendix

### Override guide

Reference for editing `migration-plan.yaml` entries (used in T2 / I3):

| Case                                                                        | Edit in plan                                                                     |
|---------------------------------------------------------------------------|--------------------------------------------------------------------------------|
| Shadow platform integration (arango-like, not in CP schema, cluster-shared) | `remoteRefPath: /<cluster>`, `create: false` (promotes to passport-tier shape) |
| Passport cred generated by EnvGene (rare, requires provider cooperation)    | `create: true`                                                                 |
| Provider-generated cred (consul-bootstrap, k8s SA)                          | `create: false`, `writeToStore: false` (gap workaround; see Gaps)              |
| Env-scoped biz cred, per-namespace granularity                              | `remoteRefPath: /<cluster>/<env>/<ns>`                                         |
| Multi-platform on cluster (two DBaaS instances)                             | `remoteRefPath: /<cluster>/<scope>` — scope segment author-chosen              |
| Biz cred pre-set by ops (compliance) — Store already seeded                 | `create: false`, `writeToStore: false`                                         |

### Provision reference - post-migration BAU credential lifecycle

Who writes credential values in each situation AFTER migration completes. This is the ongoing
operational contract. Migration itself (I4) writes all plaintext values from Git. This table
governs what happens for new envs, rotations, and provider-generated creds thereafter.

| Tier + `create`                     | Who writes value                                    | When                                 |
|-------------------------------------|-----------------------------------------------------|--------------------------------------|
| `passport-tier` + `create: false` (default) | Ops via vault CLI or Platform team's tooling | Before biz env deploy                |
| `passport-tier` + `create: true`    | EnvGene via `envgene provision-cp-creds` subcommand | Platform provisioning pipeline stage |
| `env-tier` + `create: true` (default) | EnvGene provisioning-CLI at biz env deploy        | Automatic                            |
| `env-tier` + `create: false`        | Ops via vault CLI                                   | Before biz env deploy                |
| `external-tier`                     | Ops via vault CLI or vendor SDK                     | Before any deploy consuming the cred |

Provider-generated creds (consul-server, k8s SA) do not appear in this table - the boolean
`create` cannot express `skip` semantics today. Operator handles capture out-of-band with the
workaround in the Override guide. See Gaps section for the target enum extension.

CP creds in biz env deploy are always `fail_if_absent` regardless of `create` field. Ownership
boundary is enforced: biz env pipeline never writes CP creds.
