## Проблема

Каждый ран пайплайна повторно валидирует, сортирует по схеме, дампит и записывает **каждый**
сгенерированный объект — даже когда ничего не изменилось. Ран, в итоге не дающий ни одного изменения
в репозитории, всё равно оплачивает полную стоимость их создания. На замеренном ране: flush object
store занял ~1,75с (76 файлов, ~23мс каждый, в основном сортировка по схеме и YAML-дамп),
`appregdef_render` ~1,9с, а итог рана — «no local changes to commit».

Сам рендер дешёвый (~10мс на объект). Дорогая часть — то, что идёт после: валидация по схеме, сортировка
по схеме, YAML-дамп, запись файла. Если отрендеренное содержимое совпадает с тем, что уже лежит в
репозитории, эта работа порождает побайтовый идентичный файл — значит её можно пропустить.

## Дизайн

Для каждого сгенерированного объекта считаем **канонический хэш** его отрендеренного содержимого.
Храним **манифест** на окружение, где каждому пути объекта соответствует хэш, записанный последней
сборкой. В точке записи сравниваем свежевычисленный хэш с манифестом: совпадение — репозиторий уже
держит этот объект, поэтому валидация, сортировка, дамп и запись пропускаются. Несовпадение (или
отсутствие в манифесте) — объект обрабатывается полностью, его новый хэш записывается.

```
Отрендеренный объект (в стор)
        |
        v
Канонический хэш (контент + соль схемы) <---- Манифест (путь к объекту и хэш)
        |
        | сравнение
        +--- совпадает ----------------> пропуск, файл на диске не трогаем
        |
        +--- различается / объект новый > валидация + сортировка + дамп + запись
                                                          |
                                                          v
                                                записать новый хэш в манифест
```

## Один стор на все шаги до Effective Set

Сейчас object store живёт только внутри `EnvBuildStep`, а шаг `appregdef_render` записывает AppDefs и
RegDefs на диск сам. Стор становится пайплайн-общим:

- **Жизненный цикл.** Стор открывается один раз в `run_single_env_pipeline` до первого записывающего
  шага и сливается (flush) один раз — в конце `env_build`, до генерации Effective Set. Каждый шаг,
  который порождает сгенерированный объект, кладёт его в стор, а не пишет файл.
- **Шаги, пишущие через стор.** `appregdef_render` (AppDefs, RegDefs) и всё, что `env_build` уже
  делает через стор (Applications, Namespaces, Tenant, Cloud, Profiles, Credentials). Оба флоу
  (legacy `ENV_BUILDER` и GitLab deploy) покрываются, потому что оба проходят через эти шаги.
- **Шаги вне стора.** `regdefv2_adapter` и шаги deploy-plan пишут в `tmp/render-workspace` и держат
  значения в контексте рана; эти файлы не коммитятся, поэтому они не в сторе и не хэшируются.
  Генератор Effective Set читает слитый env-каталог с диска и тоже не в сторе.
- **Корневая копия при dual placement.** При dual placement каждый AppDef/RegDef пишется и в env
  `AppDefs`/`RegDefs`, и в корневые `appdefs`/`regdefs` репозитория. Ключ в манифесте — env-относительный
  путь. Единственное решение о пропуске покрывает обе записи: `flush()` пишет корневую копию из тех же
  данных в памяти. Совпавший хэш пропускает обе копии.
- **Павший ран.** Павшая сборка ничего не пишет, как и сейчас: flush в конце `env_build` — единственная
  точка записи, а сбой до неё оставляет сгенерированные объекты несозданными, и ран не даёт коммита.
  Это меняет промежуточное состояние на диске (AppDefs больше не на диске сразу после
  `appregdef_render`), но не коммитируемый результат.

Стор и чтение/запись манифеста общие для всех шагов через один небольшой модуль. Манифест читается
один раз в начале рана и записывается один раз в конце, с записями от всех шагов, объединёнными.

## Канонический хэш

Хэш считается по отрендеренным данным в памяти, а не по файлу на диске и не по сырому YAML-тексту.

- Каноническая форма: объект нормализуется в plain `dict`/`list` (убираем `CommentedMap`/`CommentedSeq`,
  комментарии и их метаданные), сериализуется с отсортированными ключами и фиксированными разделителями,
  затем SHA-256.
- Порядок ключей, отступы, кавычки, block/flow-стиль и комментарии хэш **не** меняют.
- Порядок элементов в списках и сами значения его **меняют**: это данные, а не форматирование.
- Соль: хэш смешивается с SHA-256 **файла схемы самого объекта**. Изменение одной схемы пересортировывает
  только объекты, использующие эту схему, а не все.

Сортировка по схеме для хэша намеренно не переделывается: каноническая сериализация с отсортированными
ключами уже снимает влияние порядка ключей, а именно это и меняет сортировка по схеме. Соль схемы
покрывает случай, когда сам порядок сортировки (порядок properties в схеме) изменился, а данные — нет.

## Манифест

Один манифест на окружение, коммитится в Instance Repository рядом с описываемыми объектами.

- Место: `environments/<cluster-name>/<env-name>/.envgene/object-hashes.json`.
- Содержимое: таблица `schema_path -> хэш схемы` (считается один раз на ран) и таблица
  `относительный путь объекта -> канонический хэш`.
- Записывается пайплайном в конце `env_build` вместе с сгенерированными объектами. Ран, пропустивший
  все объекты, не пишет ни одного файла и не меняет манифест, поэтому «no local changes to commit»
  сохраняется.
- Отсутствующий, нечитаемый или некорректный манифест — это warning, а не ошибка: собираем всё и
  перезаписываем манифест.

## Хук на коммит

Манифест должен описывать то, что **в репозитории**, а не то, что создал последний ран. Между ранами
коммит, не принадлежащий пайплайну (ручная правка сгенерированного файла, внешний инструмент), может
изменить сгенерированные объекты и сделать манифест устаревшим. Хук на коммит поддерживает манифест в
согласии с репозиторием при **каждом** коммите — пайплайновом и ручном.

- Хук срабатывает на каждый push в Instance Repository и пересчитывает канонический хэш файлов
  сгенерированных объектов, коммитя манифест, если он отличается.
- Гонки с параллельными коммитами закрываются двумя способами, в зависимости от того, кто коммитит:
  - процессы **в одном воркспейсе** (детские ран-процессы фан-аута + `git_commit`) — существующим
    `envgene-git-commit.lock` (`scripts/git_commit/git_commit.py`): `flock` сериализует работу с
    одним git-index, параллельные env-раны не конфликтуют.
  - хук — **отдельная джоба** на инстанс-репо со своим контейнером, воркспейс с ранером пайплайна
    у неё общий не будет, и `flock` между джобами не работает. Поэтому хук использует тот же
    паттерн, что и `git_commit`: detached-коммит → `retry_cherry_pick_and_push`
    (`envgenehelper/git_helper.py`) — при отклонённом push (чужой коммит, в т.ч. пайплайна,
    прилетел раньше) коммит поднимается поверх и пушится снова. Манифест детерминирован
    (канонический хэш файлов), так что даже если хук и пайплайн поменяли его оба — финальное
    состояние сходится, в худшем случае это просто два коммита манифеста вместо одного.
- Для коммита, сделанного пайплайном, хук — no-op: пайплайн уже записал манифест из отрендеренного
  результата, так что репозиторий и манифест уже согласованы.
- Благодаря хуку ран больше не перечитывает сгенерированные файлы с диска. Решение — это канонический
  хэш отрендеренного объекта против манифеста, оба в памяти, ~1мс на объект.

Последствие для ручных правок: ручная правка сгенерированного файла на коммите обновляет манифест,
так что в следующем ране хэш отрендеренного объекта отличается от манифеста и объект пересобирается.
Это возвращает задокументированное поведение «содержимое будет перезаписано следующей генерацией»
без чтения диска в ране.

## Решение о пропуске

В точке записи, на объект:

| Отрендеренный хэш против манифеста | Действие |
| --- | --- |
| равен | пропустить валидацию, сортировку, дамп и запись; файл на диске не трогаем |
| отличается, или объекта нет в манифесте | полная обработка; записать новый хэш |
| манифест отсутствует / не читается / некорректен | warn; обработать все объекты; перезаписать манифест |

## Правила

- **Все сгенерированные объекты пишет один стор, сливаемый один раз, в конце `env_build`.** Ни один шаг
  не пишет сгенерированные файлы напрямую.
- **Стор не перечитывает сгенерированные файлы с диска в ране.** Сравнение — отрендеренный контент
  против манифеста. Синхронизация манифеста с диском — задача хука на коммит.
- **Хэш — по отрендеренному контенту плюс хэш схемы самого объекта.** Никогда не по байтам файла или
  YAML-тексту, никогда не хэш всех схем.
- **Манифест — на окружение**, рядом с объектами, коммитится с ними.
- **Устаревший манифест деградирует в полную сборку**, никогда в сбой и никогда в тихо устаревший объект.
- **Рендер всегда выполняется.** Пропуск убирает только то, что идёт после рендера.

## Что меняется для пользователя

- Новый коммитируемый файл на окружение: `.envgene/object-hashes.json`.
- Новый лёгкий хук/джоб на push в Instance Repository поддерживает этот файл в согласии.
- Нет изменения содержимого сгенерированных объектов. Пропущенные объекты побайтово идентичны тому, что
  пишет полная сборка.
- Логи по каждому рану сообщают, сколько объектов пропущено, сколько пересобрано.

## Ожидаемый эффект

На ране без реальных изменений: `appregdef_render` падает с ~1,9с до ~0,5–0,7с, `env_build` — с ~4,7с
до ~1,2–1,5с (рендер и хэш остаются; валидация, сортировка по схеме, дамп и запись убираются). На ране
с реальными изменениями overhead — хэш на объект плюс одно чтение и одна запись манифеста, ~0,1с.

## Вне рамок

- Пропуск самого рендера. Рендер дешёвый, и именно он делает контентный хэш безопасным.
- Хэширование входов (closure): шаблоны, ParameterSet'ы и env_definition, от которых зависит объект,
  для пропуска рендера.
- Пропуск генератора Effective Set, создание credentials и шифрование.

## Открытые вопросы

- Хук на коммит — джоб на push в Instance Repository. Его определение и CI-конфигация поставляются из
  репозитория `env-generator` и раздаются в Instance Repositories через пакет GSF (init/upgrade), тем же
  механизмом, которым GSF ведёт структуру репозитория. Подтвердить, куда в пакете `env-generator`
  положить джоб хука и как GSF init/upgrade заберёт его в существующие репо.
- Ожидается ли, чтобы ручная правка только форматирования или комментариев (те же данные) пережила ран.
  Контентный хэш не перезаписывает такой файл, пока данные не изменились.
- Стор теперь держит AppDefs до `env_build`; подтвердить, что ни один шаг между `appregdef_render` и
  flush не читает корневой каталог `appdefs`/`regdefs` с диска — сейчас файлы там есть с момента конца
  `appregdef_render`.

## Параллельные коммиты — исследовать и проверить

Отложено отдельным этапом после основного POC. Каскад из рассуждений выше зафиксирован, но ни один из
кейсов пока не воспроизводился на практике. Исследовать и проверить:

- **Ручной push во время рана.** Пайплайн генерирует из шаблонов и не читает сгенерированные файлы,
  поэтому данные не ломаются; проверить, что `retry_cherry_pick_and_push` корректно поднимает
  пайплайновый коммит поверх прилетевшего ручного.
- **Гонка коммитов хука и пайплайна за push.** Ожидание: один пушит первым, второй — поверх; манифест
  детерминирован, состояние сходится. Проверить, что в худшем случае это именно два коммита манифеста
  с одинаковым содержимым, а не расхождение.
- **Конфликт по одним и тем же строкам** (ручная правка задела строку, которую пересобирает пайплайн).
  Ожидание: cherry-pick не сходится, джоба падает после retries, следующий ран решает само. Проверить
  это поведение и зафиксировать, что оно не хуже текущего (сегодня ручной коммит в сгенерированные
  файлы так же может конфликтовать с пайплайновым).
- **Граница видимости flock:** `envgene-git-commit.lock` сериализует только процессы одного
  воркспейса (фан-аут + `git_commit`). Между джобами он не работает — проверить, что хук действительно
  ничего от ранера не унаследует и держится только на `retry_cherry_pick_and_push`.

## Идеи на потом

- **Jinja: одна общая среда (J1).** Сейчас в билде три семантики Jinja: `create_jinja_env()`
  (ChainableUndefined, кастомные фильтры), голый `Template(...)` в девяти местах (дефолтный Environment,
  без фильтров) и `Environment` на каждый paramset в `openParamset`. Этот POC кэширует каждый вид на
  месте (J2), не смешивая семантики. После — оценить сведение всех точек рендера на одну кэшированную
  `create_jinja_env()`: это уберёт дублирование поведения фильтров/undefined, но изменит рендер-семантику
  точек с голым `Template(...)` и потребует отдельный dev-design и регрессионные тесты.
- **Быстрый C-лоадер для read-only YAML.** Переключить `readYaml(safe_load=True)` в
  `envgene_shared/utils/yaml_utils.py` на `safe_load` PyYAML с C-лоадером. Все safe-чтения (в первую
  очередь 112 paramset'ов в `openParamset`) ускорятся разом, без правки call sites. Round-trip-чтения
  (объекты, записываемые обратно с комментариями) остаются на ruyaml. Нужно проверить граничные случаи
  YAML 1.1 (sexagesimal, timestamps) на реальном test_data. Трейсебилити-комментарии («параметр из
  paramset X») билд пишет на **выходные** объекты и не затрагиваются: меняется только ввод, а
  round-trip-путь записи не трогается.
- **Пропуск Effective Set по хэшу**, когда стор и манифест устаканятся: пропускать Java-прогон, если
  ран переписал ноль объектов и входы Effective Set не изменились. Блокировано на проверке, откуда в
  Effective Set берётся `DEPLOYMENT_SESSION_ID` и timestamp-подобные значения.

## Ограничения

- Минимальный код, решающий проблему. Ничего спекулятивного.
- Нет фич сверх поставленного; нет абстракций для одноразового кода; нет «гибкости» и
  «настраиваемости», о которых не просили; нет обработки ошибок для невозможных сценариев.
- Трогать только то, что нужно. Не «улучшать» соседний код, комментарии и форматирование; не
  рефакторить то, что не сломано; следовать существующему стилю.
- Удалять импорты, переменные и функции, которые стали неиспользуемыми **из-за этого изменения**. Не
  удалять ранее-existing мёртвый код, если не просят.
- Называть вещи тем, что они есть, а не типом.
- Нет комментариев в новом коде, нет docstrings, нет `# noqa` и прочих прагм. Включая тесты.
- Нет обёрток, которые только компонируют существующий вызов; выражение — в точке вызова.
- Нет лишних членов enum, где простой `==` с одним значением даёт нужный по умолчанию.
- Нет ассертов на текст логов. Тест проверяет, что warning сработал, а не текст сообщения.
- Никогда не моком компонент под тестом. Мок — только для внешних зависимостей.
